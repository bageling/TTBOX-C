# 出厂镜像 v3：为什么"刷机后激活页连不上服务器"

日期：2026-09-20　版本：1.5.21　制品：`C:\Users\Administrator\Downloads\ubuntu-22.04-preinstalled-server-arm64-orangepi-5-plus.img`

---

## 一、先说结论

镜像的网络链路**没坏**。真正把客户卡住的是两件别的事，而且都不是"服务器连不上"：

| # | 成因 | 现象 | 严重度 |
|---|---|---|---|
| 1 | **板子时钟停在 2024-10-22** | HTTPS 证书"尚未生效"，TLS 握手直接失败，前端统一显示成"连接服务器失败" | 阻断 |
| 2 | **镜像里没有模型** | core 不健康，主页 `/api/state` 轮询失败，状态徽标显示"未连接" | 阻断（激活之后的下一关） |

第 1 条是这次的真凶。

---

## 二、根因 1：无 RTC + 时钟早于证书生效日

RK3588 板上没有 RTC，掉电后时间归零。首次开机的系统时间来自
`/etc/fake-hwclock.data`，而这个文件在镜像里写的是**镜像构建日**：

```
/etc/fake-hwclock.data  →  2024-10-22 20:30:27
```

而云端 TLS 证书（Let's Encrypt）的有效期是：

```
生效 2026-06-20  ~  过期 2026-12-18
```

于是第一次开机时，盒子认为"现在是 2024 年"，去校验证书会得到：

```
SSLCertVerificationError: certificate is not yet valid
```

HTTPS 全断，激活请求根本发不出去。前端拿不到区分度，就提示"连接服务器失败"。

### 为什么我上次的探测没抓到

上次我在 chroot 里跑 `10_activation_probe.sh`，DNS、TLS、HMAC 全通——
但 **chroot 与宿主共享时间命名空间**，用的是 WSL 宿主的正确时钟（2026-09-20），
所以"时钟错"这个条件在探测环境里根本不成立。

**这就是教训：chroot 借来的环境会掩盖一整类"真机才有"的故障。**
网络能借（同 netns）、时钟也能借（同 time ns）——借来的绿不是绿。

---

## 三、根因 2：镜像里没模型

`/var/lib/ttbox/models` 下 `installed/`、`registry/` 全是空的，而
`10-device.json` 里 `model_id = "EP"`。没有模型 ⇒ core 起不来 ⇒
主页轮询 `/api/state`（core 的 IPC 接口）失败 ⇒ 状态徽标显示"未连接"。

注意这个"未连接"**和云服务器没关系**，它指的是"没连上本机 core"。
很容易被误读成"没接服务器"。

---

## 四、v3 做了什么

### 4.1 时钟下限守卫（新增）

- `/etc/fake-hwclock.data` 从 `2024-10-22` 改成 `2026-09-20 12:00:00`（落在证书有效期内）。
- 新增 `/usr/local/sbin/ttbox-time-guard.sh`：开机时若时钟早于 `2026-06-21`，
  就把时间抬到 `2026-09-20 12:00:00`，给 `systemd-timesyncd` 争取到同步完成的时间。
- 新增 `/etc/systemd/system/ttbox-time-guard.service`，已启用，排在
  `systemd-timesyncd` / `ttbox-web` / `ttbox-core` **之前**。

守卫已用桩测过两个场景（`13_timeguard_test.sh`）：

```
场景 A：模拟时钟 2024-10-22 → "时钟早于证书生效日，已抬到 2026-09-20 12:00:00 UTC"
场景 B：时钟正常 2026-09-20 → 无任何输出（不干预）
```

（chroot 内不能真的 `date -s`，会改掉 WSL 宿主时钟，所以 `-s` 打了桩，
判据与分支是真测的。）

### 4.2 预装出厂模型 EP

从开发板（已验证可用的那份）取来并烘进镜像：

```
/var/lib/ttbox/models/installed/EP/model.rknn        4,191,494 B
/var/lib/ttbox/models/installed/EP/manifest.json
/var/lib/ttbox/models/installed/EP/metadata.json
/var/lib/ttbox/models/installed/EP/validation/ok.json
/var/lib/ttbox/models/registry/active.json
```

sha256 `aca032d1…f2549`，与 manifest 声明一致；已用 ttbox 身份实读验证可读。

> 注：板端 `10-device.json` 的 `model_uploaded` 本来就是 `false`（已装模型也是 false），
> 属正常口径，**未改动**。

### 4.3 顺带修掉的构建坑

- `prepare_stage.sh` 里 `chmod 0644 "$STAGE"/factory/*` 会把新加的 `model_EP/`
  **目录**也设成 0644（去掉执行位）⇒ chroot 内连 `cd` 都进不去。
  已改成目录 0755、文件 0644。
- 收尾门禁新增一条：`__pycache__` 残留（激活探测 import 模块时会生成），已清理。

## 六、刷机后如果还是连不上，按这个顺序查

前三条是这次确认过的三大可能，按概率排：

1. **看时间**：`date`。如果年份不是 2026，说明 timesyncd 没同步上
   （NTP 走 UDP 123，部分网络会拦）⇒ 换能上外网的网口，或等几分钟再试。
2. **看 DNS**：`resolvectl status`、`getent hosts cctv2.top`。
3. **看 10046 端口通不通**：`curl -vk https://cctv2.top:10046/ttbox/api/client/card-login`
   —— 客户网络拦非标端口是最常见的外部原因。
4. 区分"未连接"是哪一个：主页徽标 = 与**本机 core** 的 IPC；
   激活页 = 与**云服务器**的 HTTPS。两个不是一回事。

## 六之二、复核（与"正在正常跑的开发板"对表）

不重跑自己的自检（那会自我印证），改为拿镜像跟开发板（192.168.0.104，四项服务全 active）逐项对表。

| 项 | 镜像 | 板端 | 结论 |
|---|---|---|---|
| `config.d/00-factory.json` | 2159 B | 2159 B | 逐字节相同 |
| `config.d/10-device.json` | 3428 B | 3428 B | 逐字节相同 |
| ufw | unit enabled，`ENABLED=no` | 同 | 均 inactive，出站 ACCEPT |
| `RELEASE_BUILD.md` | 无 | 无 | 不是缺口（release 树只有 manifest） |
| unit 依赖 | 无 `After=network-online.target` | 同 | 不插网线也能开面板 |
| `default.json` | 仅 `cloud` 段 | 60+ 键 | 仅 `cloud` 才对：源码里该文件只被 `_load_cloud_credentials()` 读，运行期配置走 core IPC |

**第一次真在镜像里跑面板**（chroot 共享宿主 netns，127.0.0.1 可用）：

- `/` → **302 → `/activate`** ⇒ 这就是客户说的"第一个验证页面"，现象落点确认。
- `/activate` → 200 / 9599 B，页内含 `/api/license/activate` 调用点。
- 假卡走一次激活 → `无法读取设备指纹（cpu_serial）`。**这是 chroot 假象**：
  宿主是 x86 WSL，`/proc/cpuinfo` 没有 `Serial` 行。板端同内核
  （5.10.0-1012-rockchip）`Serial: 9ecf266dc8154491` 存在，且 `_machine_code()`
  有双重兜底：cpuinfo Serial → core IPC `bind_device`（core 那层还读
  `/proc/device-tree/serial-number`）。
- 未知 API 未激活返 403 `activation_required`、激活后返 404 ⇒
  板端 404 / 镜像 403 的差异由此解释，不是代码分叉。

**复核结论：没有发现新的阻断项。** 交付件 sha256 复核仍为 `65436093…a77e86e4`。
