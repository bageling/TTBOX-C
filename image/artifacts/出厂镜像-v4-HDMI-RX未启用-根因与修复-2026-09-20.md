# 出厂镜像 v4：出厂 DTB 里 HDMI-RX 是 disabled

日期：2026-09-20　版本：1.5.21
现场报错：`EDID 应用失败 {"ok":false,"error":"已请求重协商，但未找到可写 HDMI-RX HPD 节点"}`

---

## 一、结论先说

**这不是 EDID 的毛病，是设备树根本没把 HDMI-RX 打开。**

出厂 DTB 里 `hdmirx-controller@fdee0000` 的 `status = "disabled"`，
而 `extlinux.conf` 里没有任何 `fdtoverlays` 指令 ⇒ 那个 `rk3588-hdmirx.dtbo`
只是躺在磁盘上，**从来没被应用过**。

后果远不止 EDID 那一句报错：

| 症状 | 原因 |
|---|---|
| EDID 应用报「未找到可写 HDMI-RX HPD 节点」 | `/sys/class/hdmirx/hdmirx/status` 压根不存在 |
| **HDMI 采集整体不可用** | `/dev/video0` 不存在（同一个驱动没 probe） |

也就是说，客户拿到的盒子**核心功能（HDMI 输入 → AI 推理）是废的**，
EDID 报错只是最先露出来的那一个口子。

---

## 二、证据链（与正在正常跑的开发板逐字节比对）

开发板 192.168.0.104 = **Orange Pi 5 Plus**，与镜像 `orangepi-5-plus`
同型号同内核（5.10.0-1012-rockchip），所以可以直接对表。

```
镜像 DTB  280076 B   sha256 7b8cc892…   文件内 "disabled" 出现 192 次
板端 DTB  280072 B   sha256 277d9de8…   文件内 "disabled" 出现 191 次
                    ↑ 小 4 字节
```

逐字节比对（`cmp -l`），193076 之前只有 3 处**头部长度字段**不同（8/16/40），
真正的语义差异只有一处：

```
偏移 193076：镜像 长度=9  内容 "disabled\0"
             板端 长度=5  内容 "okay\0"
```

9 − 5 = 4，正好对上文件大小差。偏移附近的上下文属性是
`rockchip,hdmirx-ctrler` / `hdmirx_regs` / `hclk_s_hdmirx` / `cec`
⇒ **确认就是 `hdmirx-controller@fdee0000` 的 status**。

板端实测对照：

```
/proc/device-tree/hdmirx-controller@fdee0000/status = okay
/sys/class/hdmirx/hdmirx/status  root:ttbox 0660   ttbox 可写
/dev/video0 存在
ttbox-edid.service 开机成功：{"ok":true,"hpd":"rehandshake",...}
```

---

## 三、为什么之前的自检是假绿

旧自检只断言了两句：

- `hdmirx overlay : /usr/lib/firmware/.../overlay/rk3588-hdmirx.dtbo`（文件在不在）
- `boot 配置含 overlay 配置（静态可判）`

**文件在 ≠ 生效。** dtbo 存在不代表有人应用它；
`extlinux.conf` 里连一行 `fdtoverlays` 都没有，它永远不会被加载。
这是同一类错误的第三次重犯（chroot 借来的绿、find 软链不下降、
文件在 ≠ 生效）——**凡是"存在性"断言，都要问一句"谁会真的去用它"**。

已在 `05_selfcheck.sh` 的 I 段补上硬断言：直接校验 DTB 的
sha256 与 `disabled` 计数（已启用 = `277d9de8…` / 191；出厂未改 = `7b8cc892…` / 192）。

---

## 四、修法（及为什么不是"加 fdtoverlays"）

**做法**：把已验证可用的 DTB 装进镜像
（`image/steps/04d_hdmirx_fix.sh`，源文件 `image/factory/rk3588-orangepi-5-plus.dtb`）。

**为什么不用 `fdtoverlays` 应用 dtbo**：
那依赖 u-boot 的 sysboot 对该指令的支持，**没在真机上验过** ⇒ 不可靠。
而"直接装已验证的 DTB"是板上正在跑的那一份，
且已逐字节证明它与出厂 DTB 的唯一差异就这一处 status，改动面最小、可验证性最强。

`04d` 的三条硬断言（任一不过就 FAIL）：

1. 装后 DTB sha256 == `277d9de8…`
2. 装后 `disabled` 计数 == 191
3. dtbo 仍保留在盘上（不依赖，但保留）
