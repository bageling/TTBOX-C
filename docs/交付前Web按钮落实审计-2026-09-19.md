# TTBOX Web 面板按钮落实审计（2026-09-19）

审计对象：`plugins/web/templates/index.html`（面板前端，单文件约 7600 行）+
`plugins/web/bin/ttbox-web.py`（后端，约 4300 行）+ `core/`（C++ 引擎）。

审计动机：上一份《交付前Web实测报告-2026-09-19》只回答了"按钮点不点得动"。
这一轮把口径收紧成"点下去到底有没有真实副作用"——逐控件从 DOM 追到 Core，
或追到文件系统 / systemd / 硬件。**点得动 ≠ 落实到位**，本轮就是专门抓这个差。

本报告为一次性报告；面板功能现状的长期描述仍以相关主题文档为准。

> **修复进度（2026-09-19 起）**：第一档四处撒谎已修（提交 `fe8b9fa`）。
> 第二档「静默无效」的修复为分批实施，批次依赖、当前状态与验收证据统一记在
> [面板功能补齐实施计划-2026-09-19.md](面板功能补齐实施计划-2026-09-19.md)（活真源）。
> 本报告正文保持审计当时的原样，不改写，以免失去"当时看到了什么"的对照价值。

## 一、审计方法与判定口径

五路并行分页审计，每路只读，不改代码。每个控件按同一条链追：

```
DOM 控件 → collectConfig 采集 → web_body_to_profile 翻译
        → Core 结构体字段 / 算法消费 → 真实副作用（文件 / socket / systemd / 硬件）
```

链路任意一环缺失即记为断链或假落实。判定分四档：

| 档 | 含义 |
|----|------|
| **A 真落实** | 点下去有真实、可验证的副作用，且回读与事实一致 |
| **B 半落实** | 做不了的部分明确告知（诚实空壳），不撒谎，但功能缺失 |
| **C 断链** | 前端采集了，中间某层静默丢弃，用户以为生效了其实没有 |
| **D 假落实** | 撒谎：返回硬编码成功 / 回读硬编码真值 / UI 亮绿灯但物理事实相反 |

C 和 D 是要命的两种：C 是"点了没用还不告诉你"，D 是"点了没用还告诉你成功了"。

## 二、总体结论

九个页面合计审计约 **95 个控件**，按各路的原始计数：

| 页码 | 范围 | A | B | C | D |
|------|------|---|---|---|---|
| 01 | 总览 + 全局交互 | 15 | 1 | 0 | 3 |
| 02/03 | 热键 + 移动控制 | 22 | 4 | 13 | 0 |
| 04/07 | 辅助功能 + 预设管理 | 8 | 0 | 6 | 2 |
| 05 | 模型库 | 9 | 0 | 4 | 1 |
| 06/08/09 | 显示鼠标 + 系统 + 风扇 | 8 | 6 | 3 | 3 |

（各路对子项粒度的切法不完全一致，这张表的数字不能强行相加成全局总数，
只能横向看每页的分布。）

真实落实的大约六成——启动/停止、主题切换、压枪、显示器配置、模型切换与导入、
预设保存、危险操作二次确认这些主干是真的。剩下四成的毛病集中在三种病：

1. **前端采集了、翻译层丢字段**。PID 区 8 个输入框、风扇整组、连点/自动开火/自动背闪三区，
   前端 DOM 齐全、`collectConfig` 也收上来了，但 `web_body_to_profile` 里根本没有对应分支，
   字段在这一层被静默丢弃，永远到不了 Core。
2. **回读硬编码**。`profile_to_web` 把辅助功能几组恒返空 `{}`（ttbox-web.py:1170-1172），
   `hotkey_guard` 回读恒 `{'enabled': False}`，`collect_web_state` 里 `hotkeys_suspended`
   恒 `False`（ttbox-web.py:1279）。用户改完、刷新、发现"又变回去了"，就是这里造成的。
3. **撒谎式成功**。最典型的三处：`apply_mouse_config` 恒返 `applied: True`
   （ttbox-web.py:3823）、`/api/system/storage` 恒报「尾部还有约 X GB 可扩空间」
   （ttbox-web.py:1795-1807，实际是硬编码）、重启/关机 fire-and-forget 立刻返成功。

第 3 类里最该挨骂的是存储那处：它不是"没实现"，是**主动编了一个不存在的容量数字**
去骗用户点按钮，比纯空壳更坏。

## 三、逐页明细

### 01 总览 + 全局交互

真落实：启动 / 停止（终到 `core/src/app/Application.cpp:1426` 真 start/stop）、
主题切换（localStorage `aiassistance_theme`，index.html:6509，真持久化）。

**D-1｜授权修复按钮是诚实空壳，但归到了 D**
`/api/system/reactivate`（ttbox-web.py:1876-1885）无条件返回固定错误文案。
不打 500、不撒谎成功，只固定说"不行"——按口径这算 B，但对用户是死按钮，需要明确处理。

**D-2｜控制失败的报错被改写（误报）**
`start_control`（ttbox-web.py:3556-3558）把 Core 返回的所有非模型类失败
一律改写成"未导入模型"。真实原因（比如 socket 不通、权限不足）被盖掉，
和 P0-1 里那条"把真因盖成 Core 未运行"是同一个坏习惯的第二处。

**D-3｜热键暂停状态恒显假绿**
`collect_web_state` 硬编码 `hotkeys_suspended: False`（ttbox-web.py:1279）。
哪怕热键已被挂起，面板上永远是"正常"。这是 D 档里最隐蔽的一种——它不报成功，
它只是永远显示一个好看的默认值。

### 02 热键 + 03 移动控制（C 最多的一页：13 项）

真落实：保存主链、预设自动保存。

**C-1｜PID 区一整块不落地**
ki×2、丢失帧、开火延迟 Y 整组×3 等共 8 个输入框，前端采集 → 翻译层无分支 →
Core 结构体无字段 → 算法不消费。四层全断，用户调的是空气。

**C-2｜多热键卡只译 profiles[0]**
一个动作配了多个热键卡时，翻译层只取第一个。第二张以后静默失效。

**C-3｜sensitivity 被恒覆盖**
面板上的灵敏度被 `p0.sensitivity` 无条件覆盖，用户改的值不生效。

**C-4｜hotkey_guard 双重断链**
保存不入 Core（翻译层断），回读又硬编码 `{'enabled': False}`，徽标再硬编码 `False`。
三处各自独立地断，改一处不会好。

**C-5｜持续提前量三参数是 Core 保留字段**
渐入 / 渐出 / 近距离禁用这三项，Core 里字段在、算法不消费。属于"预留了没接"。

### 04 辅助功能 + 07 预设管理

真落实：压枪是这一页唯一全通的链（→ `MouseTypes.hpp:163` RecoilConfig →
`AimThread.cpp:116/285`），端到端可用。

**C-6｜连点 / 自动开火 / 自动背闪 / 准星找色四区整体断链**
`profile_to_web` 在这四组恒返空（ttbox-web.py:1170-1172），翻译层无分支，Core 无概念。
补充核实：Core 里 `crosshair_detected` / `AimPoint crosshair`
（`core/src/pipeline/AimTargetTask.hpp:19-20`）是**没人读也没人写的死声明**，
所以"准星找色"确实是从头缺到尾，不是接错线。

**D-4｜预设导出返回 API 信封而非文件本体**
导出拿到的是一个 JSON 信封，不是可再导入的预设文件。
"导出 → 再导入 → 加载"这条回路恒静默无效——导入不报错，加载也不报错，就是没效果。

**C-7｜"导入后名称"被后端忽略**
`import_preset`（ttbox-web.py:2963）不读前端传的名称字段。

### 05 模型库

真落实：复制设备码、RKNN 直传导入、卡片切换模型（真 MODEL_ACTIVATE）、绑定预设。

**C-8｜ONNX 导入前端未接线**
前端固定打 `/api/models/import`，被 ttbox-web.py:2674-2679 拒。
但后端**转换链已经实现**了——这是前端漏接一根线，属于最容易修的一类 C。

**C-9｜HEF 导入后端无分支**
前端有入口，后端 `import` 里没有对应处理分支。

**D-5｜"切换模型自动加载预设"是假承诺**
`select_model`（ttbox-web.py:2759-2769）永不返回 `created_default_preset`，
前端却按"会自动建默认预设"的话术展示。

**C-10｜模型卡片标题退化**
`list_models`（ttbox-web.py:2418-2448）与 `_models_view`（ttbox-web.py:1192-1220）
返回形状漂移，缺 `display_name`，卡片标题退化成原始 id。
板端实测里那行 `320 ??? 0907` 就是这一族。

**关于 label 乱码**：编码链路本身查过是安全的，乱码的具体产生点尚未定位到，
这一条列未决。

### 06 显示鼠标 + 08 系统 + 09 风扇

真落实：显示器侧整条是真的——白名单合并 → 写 `hardware_display.json` →
`edid_apply.sh` 重握手 → `mode_builder` 消费，闭环。

**C-11｜loopout_pixel_format 落文件无下游**
写进了配置文件，但没有任何一方读它。

**D-6｜鼠标侧整片假落实（本页最严重）**
`apply_mouse_config` 恒返 `applied: True`（ttbox-web.py:3823）；
Core 里没有 `usb_*` / `proxy_mode` 任何成员；`usb-proxy` 服务从不重启；
前端还谎报"Windows 会重新枚举"。四层全假，且**主动告诉用户成功了**。

**D-7｜风扇运行状态与物理事实相反**
`_fan_control_payload()`（ttbox-web.py:2159）里 `'enabled': False` 硬编码。
而 `core/src/app/Application.cpp:456-465` 开机就把 `/sys/class/hwmon/hwmon8/pwm1`
写成 255（满转）。也就是说**风扇实际在满转，面板显示"未启用"**。

**C-12｜风扇配置四层全断**
前端采集 → 翻译层无 `fan` 分支（直接丢弃）→ Core 无 `fan` / `pwm` 可配字段
→ `Application.cpp` 只有开机那一次硬编码写 255。
和鼠标侧一样是四层断，区别是风扇至少真在转。

**D-8｜扩容的假数据（前序已记录，本轮再次确认）**
`/api/system/storage`（ttbox-web.py:1795-1807）的 `rootfs` 整流是硬编码，
还带一句 `message: 检测到磁盘尾部还有约 X GB 可扩容空间`；
`/api/system/storage/expand`（ttbox-web.py:1812-1818）只跑一次 `lsblk` 就返回
"扩容需重启进恢复流程"。全仓无任何真实分区 / 文件系统操作代码。

**其他系统项**：改主机名调 `hostnamectl` 必败，但真实错误有外显（B 档）；
改端口是 fail-closed 明确拒绝（B 档，符合设计）；
检查更新的错误码能 toast，但中文 detail 没透出（B 档）；
重启 / 关机 fire-and-forget 立即返成功（D 档，且这两个按钮实际位于 01 页）。

## 四、最该修的（按交付风险排序）

### 第一档：撒谎，必须先修

1. **存储假数据**（D-8）。删掉那句编造的容量结论，在真扩容落地前让按钮老实说"未实现"。
   一个编造的数字比一个灰色按钮危险得多。
2. **鼠标侧假成功**（D-6）。`applied: True` 改真实结果，或把整组置灰并说明未实现。
3. **风扇状态反相**（D-7）。`enabled` 至少读真实 pwm 值，别再恒 False。
4. **重启 / 关机假成功**（D-8 同族）。改成等 systemd 真实返回，或明确说"已下发，结果未知"。

### 第二档：静默无效，用户会以为生效了

5. **PID 区 8 个输入框**（C-1）。要么补齐四层，要么从面板移除——留着比删掉更坏。
6. **连点 / 自动开火 / 自动背闪 / 准星找色四区**（C-6）。同上，补或删。
7. **hotkey_guard 双重断链**（C-4）。保存和回读两处都得修。
8. **预设导出非文件**（D-4）。导出必须产出可再导入的文件。
9. **ONNX 导入前端接线**（C-8）。后端已有，前端漏接一根线，性价比最高。

### 第三档：会误导但不致命

10. `start_control` 报错改写（D-2）——第二条同样的坏习惯。
11. 多热键只译 `profiles[0]`、sensitivity 被覆盖（C-2/C-3）。
12. `hotkeys_suspended`、模型卡片 `display_name`（D-3/C-10）。
