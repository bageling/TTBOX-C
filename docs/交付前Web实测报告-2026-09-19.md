# TTBOX Web 面板实测报告（2026-09-19）

被测对象：`http://192.168.0.104:8000/`（RK3588 板端已部署版本 1.4.6）
测试方式：Chromium 真机浏览器自动化（agent-browser），逐页遍历 + 记录每一笔 XHR 的
请求/响应/状态码，必要时上板只读核验（SSH）与直接 curl 交叉验证。
测试时间：2026-09-18 晚 — 2026-09-19 上午。
本报告为一次性报告；面板功能现状的长期描述仍以相关主题文档为准。

---

## 一、总体结论

面板的「展示 + 只读 + 门控」这一层基本是好的：9 个页面都能加载、导航与分节切换正常、
启动/停止这类走独立端点的操作真实可用、危险操作的二次确认与 fail-closed 拒绝都符合设计。

但「保存配置」这一整条链路是断的。**面板上凡走 `PUT /api/config` 的修改（热键、PID 参数、
辅助功能、预设参数、风扇开关等）全部失败**，且报错文案把真实原因盖成了「Core 未运行」。
这属于交付阻断级问题：用户点任何「保存」，都会看到一句与事实不符的报错，且改动不落盘。

另有一条 500：显示器配置保存（`PUT /api/hardware/display`）因文件权限被拒。

结论：**不通过**。至少 P0-1、P1-1、P1-2 三条修复并回归后，才谈得上交付。

（后记：这三条已在本报告出具后修复于源码，见第六章；但**尚未打包上板**，板端现象同本文。）

## 三、发现的问题（按严重度）

### P0-1　面板全部配置保存失败，且报错文案误导（交付阻断）

**现象**：02/03/04 页改任一参数、09 页勾开关，都会发 `PUT /api/config` 并得到
`503 {"error":"Core 未运行，配置未保存（请先启动 ttbox-core）"}`。而板上 `ttbox-core` 明明
`active (running)`，IPC 通的（`sudo -u ttbox` 直连 `/run/ttbox/core.sock` 发 `GET_STATUS`
正常回包）。

**根因（已定位到行）**：
1. 前端每次保存提交**全量**配置，其 `capture` 段带 `crop_size: 1`（无 width/height）。
2. `plugins/web/bin/ttbox-web.py:947-950` 把 `crop_size` 直译成
   `capture.width = capture.height = 1`。
3. core（`core/src/app/Application.cpp:1248` → `RuntimeProfile::validate`）校验不通过：
   `profile 校验失败: capture.width 非法（0=全帧，或需在 64~3840 之间）`，`status=1`。
4. `ttbox-web.py:2062-2065` 把任何 `status != 0` 一律包装成
   「Core 未运行，配置未保存」，**丢掉 core 的真实错误**。

**取证**：把面板实际发出的 2680 字节请求体导出，在板上用 web 自身代码重放同一流程，得到
core 原话：`SET_CONFIG status: 1 error: profile 校验失败: capture.width 非法（0=全帧，或需在 64~3840 之间）`。
同一流程若只提交 `{"fan_control":{...}}`（不含 capture）则 `status:0 applied+persisted`——
证明链路通、是这份 payload 触发校验失败。

**附带**：`fan_control` 在 `web_body_to_profile()` 里根本没有翻译分支（仓库 HEAD 也无），
配置文件中无该键，core 静默丢弃未知键 ⇒ 即使修好 width，风扇设置依然存不下来。

**影响面**：热键、PID/拉枪曲线/持续提前量、压枪/开火/连点/背闪/准星、预设参数项、
风扇控制——面板上所有"保存"类操作。

**修复方向（三件）**：
- `web_body_to_profile` 的 capture 翻译：`crop_size<=0` 或非法值时按 0（全帧）处理，
  不要生成 <64 的非零值；或前端 `collectConfig` 不要提交非法 crop_size。
- `PUT /api/config` 失败分支：把 core 返回的 `error` 透传给前端（目前被固定文案覆盖），
  并区分"core 不可达"与"core 拒绝校验"两种 503。
- 补 `fan_control` 的落盘通道（翻译键 + core 侧支持），否则面板应把该区标为"未生效"。

### P1-1　显示器配置保存必然 500（文件权限）

**现象**：06 页「保存并应用」→ `PUT /api/hardware/display` → 500 Internal Server Error。
**根因**：`ttbox-web.py:4020` 写 `/opt/ttbox/config/hardware_display.json`，
该文件 `root:root 644`，`sudo -u ttbox test -w` 判定 **NOT_WRITABLE**，
而 web 服务 `User=ttbox`。journal 抓到同函数栈的
`PermissionError: [Errno 13] Permission denied: '/opt/ttbox/config/hardware_display.json'`。
**同类**：与 OTA 复核报告里的 P0-1（发布树属主污染）同族——都是"文件属主/权限 vs 服务运行身份"不匹配。

### P1-2　存储扩容按钮永久禁用，"刷新容量"结果被轮询打回

**现象**：点「刷新容量」后，`/api/system/storage?force=1` 返回 `expandable:true`，
但页面立即回到「未读取」、`expandStorageButton` 回到 disabled，用户点不到扩容。
**根因**：`templates/index.html:10349` —— 每秒一次的 `/api/system` 轮询把
`payload.storage`（只有 `free/percent/total/used`，**没有** `rootfs` 字段）交给
`renderStorageExpansion()`；该函数按 `rootfs.expandable` 决定按钮禁用与 pill 文案，
空对象 ⇒ `expandable=false` ⇒ 按钮禁用、pill「未读取」。刷新结果最多存活 1 秒。
**取证**：页面内直接调 `refreshStorageStatus()` → `disabled=false pill=可扩容`；
之后被轮询重置。后端 `GET /api/system/storage` 与 `POST /api/system/storage/expand` 均正常。

### P2-1　"检查更新"的错误原因不呈现给用户

`/api/update/check` 返回 503 后，UI 状态仍停在「待检查 / 暂无更新信息」，
用户看不到"分发服务器未配置"这个原因。建议在更新区展示 `error/detail`。

### P2-2　版本显示与实际安装不一致

面板「当前版本 1.4.5」（core `GET_STATUS` 投影），板上
`/opt/ttbox/current → releases/1.4.6`、VERSION 文件也是 1.4.6。
`kAppVersion='2026.08.03.1'`（面板版）、core 版、release 版按设计三名分离，
但把 1.4.5 标成「当前版本」会让用户对"装没装上新版"产生误判。

### P2-3　"修改局域网名称"是死功能

界面提供输入框与「应用」按钮，但 web 无特权，`hostnamectl` 必然报
`Interactive authentication required`，且输入框会被轮询复原。
建议二选一：加特权通道（与 OTA 任务文件同思路），或把该输入框下线/置灰并说明。

### P2-4　模型 label 数据层乱码

模型列表 `label` 字段实为 `"320 ??? 0907"`（`id` 是正常的 `320dawan0907`），
即注册/上传时原文件名中的非 ASCII 字符被写成了字面 `?`（0x3F），不是显示层问题。
建议排查模型导入时的文件名编码处理（参考注册表生成路径）。

### P2-5　OTA 状态残留误导

`/opt/ttbox/state/ota_status.json` 仍是 `{"state":"SUCCESS","version":"9.9.9"}`，
但 current 已回滚到 1.4.6。`/api/update/status` 会把这个残留当"最近一次成功"展示。
建议回滚路径同步更新该状态文件。

### P2-6　板上前端比仓库 HEAD 旧

板上 1.4.6 的风扇页只有 2 个控件（开关 + 温度来源），仓库 HEAD 有 6 个（含 4 个滑杆）；
说明板端并非 HEAD 构建。继续在板上测"用户会看到什么"没问题，但要清楚
**板上现象 ≠ HEAD 现象**，P0-1 的两处代码在 HEAD 里同样存在（已核对 :947-950、:2062-2065）。

### P2-7　存储扩容功能本身未实现（只有壳）

`GET /api/system/storage`（`ttbox-web.py:1795-1807`）的 `rootfs` 整块是**硬编码**：
`can_expand`/`expandable` 恒为 `True`，`message` 把"根分区剩余空间"直接说成
"磁盘尾部可扩容空间"（两者不是一回事——要能扩，得看 `mmcblk0p2` 分区之后还有多少未分配空间）；
`method: growpart` 也只是写死的字符串，没有任何真实分区探测。

`POST /api/system/storage/expand`（`:1812-1818`）只跑一条 `lsblk` 打印就返回
"扩容需重启进恢复流程"，**不写任务文件、不做 growpart/resize2fs**。
全仓 grep：`growpart` 仅此一处字符串，`resize2fs`/`sfdisk`/`parted`/`e2fsck` 零命中，
`scripts/` 下无任何存储运维脚本。

结论：这一页对用户呈现的是"可扩容 8.1 GB"，点了却什么也不会发生。要么实现
（可照抄 OTA 的 `.path`+root oneshot 特权通道范式：web 写 `/var/lib/ttbox/storage/jobs/*.json`
→ root worker 落盘归档 + 状态文件 → 前端 1s 轮询终态），要么把该区明确标为"未启用"。

## 四、测试方法与可复现要点

- 浏览器：`agent-browser` + Chromium，真机访问 `http://192.168.0.104:8000/`。
- 页面结构：9 个 `page-card`；导航按钮 class `module-tab`；切换靠 `is-active`。
- 请求取证：注入 `fetch` 包装记录 `REQ/RESP(status+body)`；导出面板全量请求体。
- **坑一**：`confirm()` 原生弹窗会冻住 JS，导致 CDP `Runtime.evaluate` 超时、守护进程卡死。
  必须先覆写 `window.confirm`（默认返回 false），再逐个按钮放行，避免误触真实重启/关机。
- **坑二**：同一批命令里连续多次调用会出现 `os error 10060`，需把动作拆细、用后台任务保活守护进程。
- 板端核验：`plink -ssh -pw root -hostkey SHA256:JCSZToi0… root@192.168.0.104`（只读命令 + 一处 `sudo -u ttbox` 探活）。
- 收尾核验：current=1.4.6、`10-device.json` 内容未被污染（capture width/height 仍为 0、
  无 fan_control 键）、测试预设已删（presets 目录为空）、四个 ttbox 服务 active、
  流水线已停（未遗留运行中的推理）、未重启/关机。
