# 主链清理与死代码盘点方案

> 业主诉求：「现在要主链干净，拟人化什么的死代码也要盘点出来。」
> 本方案只回答一件事：**主链上哪些是"真主链"，哪些是附加物，哪些是死代码/死字段/幻觉注释，以及怎么清。**
> 全部结论基于 2026-10-07 逐文件 grep + 读码核实，非推测。行号以当前工作区为准。

---

## 0. 一句话结论

主链 = **采集 → 预处理 → 推理 → 解码 → 选靶 → 误差 → PID → 输出**，这 8 段是干净的。
「乱」和「拟人化死代码」都集中在**输出链的附加物**里：7 个拟人化相关模块中，
**1 个纯死代码（MotionMerge）、1 条幻觉注释链（humanize）、2 个死字段、2 个无面板通路但已接线的半死模块**。
清理分 4 批，每批单文件、可独立 revert。

### 2.2 逐个证据

**#1 PullCurve —— 活，但带一个死字段**
- `PullCurveConfig.enabled = true`（`MouseTypes.hpp:167`），是拟人化家族唯一默认开的。
- 前端有控件（`index.html:479-484` + `panel/00-const.js:118` + `10-flow.js:2418`），后端翻译层 `controller_bools()` 有 `pull_curve_enabled`。
- **死字段**：`jitter_px`（`MouseTypes.hpp:169`）——`PullCurve.hpp` 注释明写「2026-09-29 删除自研抖动…字段保留…本模块不再消费」，`PullCurve::apply()` 算法层确实已不读它（只读 `enabled/min_distance/strength`）。
  ⚠ **精确口径（复核修正）**：它**不是**「全仓只有定义那一行」。实测 `jitter_px` 代码命中 5 处——定义（`MouseTypes.hpp:169`）+ 序列化 to_json（`RuntimeProfile.cpp:404`）+ 反序列化 from_json（`RuntimeProfile.cpp:683`）+ 2 处测试赋值（`test_mouse.cpp:633`、`test_pull_curve_aimthread.cpp:94`）。即「算法层零消费，但序列化层仍在搬运」。删字段须连带处理 `RuntimeProfile.cpp:404/683` 两处。

**#2 PersonalMotion —— 活，但带 3 个「活链路死消费」的死字段**
- `PersonalMotion::scale` 在 `AimThread.cpp:531` 实打实调用，`personal_gain` 直接乘进 `scaled_x/y`。**这是活的。**
- 后端 `core/src/web/domain/motion.cpp` 有完整 motion-profiles CRUD + motion-training sessions，前端 `motion_training.js` 有控件。
- ★ **死字段（活链路、死消费）**：`speed_blend` / `reaction_blend` / `max_reaction_delay_ms` 三个键**从头到尾端到端空转**：
  1. 前端 `motion_training.js:116-118/708-710` 发这三个值（有滑杆 UI）
  2. 后端 `motion.cpp:57-61` 存进 mix、`motion_store_session.cpp:235-246` 校验并写 active.json
  3. `apply_personal_motion_to_core`（`motion.cpp:60-61`）再写进 `personal_motion` JSON、`SET_CONFIG` 传给 core
  4. ★ **但 core 的 `RuntimeProfile.cpp:696-704` 反序列化只读 `enabled` / `curve_blend` / `knots`，这三个键被静默忽略**
  ⇒ 用户在 motion 训练页调这三个滑杆，数据能存能传，但**对实际输出零影响**。
- 这是记忆里「假开关三种真因」第①种（配置项只在序列化、主链 0 消费点）的又一实例：不是「字段删了但翻译层还在收」，而是「训练层还在存、消费层已经不读」。

**#3 ContinuousLead —— 半死（后端可达、前端无控件）**
- `ContinuousLeadConfig.enabled = false`，`AimThread.cpp:551` 调用 `continuous_lead_.apply(...)`。

**#4 PersonalTrajectoryShader —— 半死（后端可达、前端无控件）**
- `PersonalTrajectoryConfig.enabled = false`，`AimThread.cpp:685/697/710` 完整调用链。
- 后端 `controller_bools()` 有 `personal_trajectory_enabled` 键，翻译层完整。
- 前端 `index.html` / `panel/*.js` **0 命中** ⇒ 同上，面板无开关。
- ⚠ 额外：这是 N1 守卫⑥ `goal_progress_` 单调闩锁（`PersonalTrajectoryShader.hpp:92`）的所在地——**一个前端够不着的模块，藏着一个跨帧状态污染的 P0 级 NaN 缺陷**。

**#5 JitterFeedforward —— 半死（配置完全无通路）**
- `JitterFeedforwardConfig.enabled = false`，`AimThread.cpp:482/:699` 调用。
- `RuntimeProfile.cpp:565-571/852` 有序列化（`jf.set("enabled", ...)` 等）。

**#6 MotionMerge —— ★★ 纯死代码（生产零调用）**
- 全仓 grep `MotionMerge::merge`：**生产零调用**，只有 `test_mouse.cpp:298-348` 在用。
- 真实「物理+AI 合并」不在 core，在 **usbproxy 侧**（`mouse_control_merge_report`，见教训台账「搭车投递」），core 的 `AimThread` 直接 `output_->send(OutputAction{move_x, move_y, ...})`，`OutputBackend` 里根本没有物理位移合并逻辑。
- ⇒ `MotionMerge.hpp`（54 行）是**早期设计残留**，V1 只实现一种策略、且这个策略从未被生产接线。

**#7 humanize —— ★★ 幻觉注释（链已删，注释还在撒谎）**
- 全仓 grep `humanize`，**代码零命中**，只有 5 处注释：
  - `AimThread.cpp:758`「BB 拟人化链（humanize.enabled 时替掉旧 personal_shader_）」
  - `AimThread.hpp:232`「两条拟人化链（humanize / personal_trajectory）都只往输出里加抖动」
  - `MouseTypes.hpp:264`「删掉 humanize_jitter_*」
  - `test_mouse.cpp:617`「对应 humanize 用例」
- ⇒ `humanize` 这条链**已经被删干净**（`MouseTypes.hpp:264` 记录了删除），但 `AimThread.cpp:758` / `AimThread.hpp:232` 的注释**仍宣称它存在**，且说「两条链互补叠加」——**实际只有 `personal_shader_` 一条链在跑**。
- 这是「注释撒谎」的又一实例，会误导后人以为有第二条拟人化链要维护。

## 4. 清理批次方案

> 红线：**「搬运」与「加守卫」不得同批**；每批独立 commit、可独立 revert。
> 验收统一两层（§9.0）：单元测试走 `C:/ttbox-local/core/build-ascii` ctest，上板行为走 WSL 交叉编译。
> ★ 验收口径（审查修正）：ctest 的 **44 = add_test 条目数**，删内部 TEST block **不改变 44**。验收看「ctest 44 全绿不变 + `--gtest_list_tests` 核对内部 TEST 数下降」+「结构性删除的字段/函数全仓 grep 0 命中」。

### 批 A：删卡尔曼死链（`TargetSelector.{hpp,cpp}` + `test_bytetrack_upgrade.cpp`，一个 commit）
三块分开（详见主评审 §5.10）：删 `kalman_predict()` + 拆 `kalman_update()` 保 `track_seen()` 三行 + 删状态字段。
★ **字段删除清单（审查补全）**：8 状态字段（kx/ky/kw/kh/vx/vy/vw/vh）+ **`pred_cx/pred_cy`（独立 2 字段，:207）** + **`created_ms`（write-only，只写 :762 不读）** + `confirmed`（零读取）+ `use_kalman_predict` + **`kalman_velocity_gain`（:129）/`kalman_max_speed_px`（:130）两个 config 字段**。
★ **绝不可删（活字段）**：`track_buffer_frames`/`max_tracks`/`last_seen_ms`/`hits`/`cx`/`cy`。
★ **测试改写范围（审查修正）**：**Case3/4/5 三个**，不是 Case4/5 —— Case3 `bytetrack_kalman_velocity_learned`（`:77`，断言 `:90 tr.vx > 0.0f`）直接依赖被删的 `vx` 字段，不改会编译失败。Case1/2（track 生命周期/max_tracks 封顶）测的是活字段，保留。
验收：`.hpp/.cpp/测试一个 commit`（拆开则中间态测试引用已删字段编译不过）；ctest 44 全绿；`kalman` 相关字段全仓 grep 0 命中；轨迹淘汰行为不变。

### 批 B：删纯死代码 + 幻觉注释（两个独立 commit）
1. commit 1：删 `MotionMerge.hpp` + `test_mouse.cpp` 的 **5 个 TEST block**（`:294 mouse_merge_no_ai_passthrough_unchanged` / `:304 ai_only` / `:312 ai_plus_physical` / `:320 block_x_and_y` / `:337 int16_clamp`）。header-only，CMakeLists 无单独引用，无构建系统改动。

验收：ctest 44 全绿不变 + `--gtest_list_tests` 显示 ttbox_core_tests 内部 TEST 数 **-5**；注释不再提 humanize。

### 批 C：删死字段（**两个独立 commit**：jitter_px 与三键无耦合，混一起会 revert 一项连带另一项）
commit 1（jitter_px）：删 `MouseTypes.hpp:169` + `RuntimeProfile.cpp:404/683` + `test_mouse.cpp:633` + `test_pull_curve_aimthread.cpp:94`（显式置 0 保基线，删掉即可）。

### 批 D：半死开关的处置（业主定方向，先不动代码）
`ContinuousLead` / `PersonalTrajectory` / `JitterFeedforward` 三个模块**代码都活着且已接线**，只是前端无控件。这是**产品决策**，不是死代码：
- 选项 1：补前端控件，让业主能用（收益：拟人化真正可用；成本：改 3 处前端 + 翻译层）

## 5. 主链「干净」的最终形态

清理完成后，主链输出段从「7 个拟人化附加物」收敛为：

```
误差(control_x/y) → PID → out_gain
  ├─ personal_gain  （#2 PersonalMotion，活，保留）
  ├─ pull_curve      （#1 拉枪弧线，活，保留）
  ├─ continuous_lead （#3，业主定：补控件 or 删）
  └─ personal_shader （#4，业主定：修 P0 + 补控件 or 删）
→ deadzone → clamp → HID
```

删掉的：`MotionMerge`（死）、`humanize`（幻觉注释）、3 个死字段、`jitter_px`（死字段）、卡尔曼死链。

## 6. 待业主拍板的 2 个决策点

1. **批 D 三个半死模块的去向**：补控件（能用）还是废弃（删代码）？我建议：JitterFeedforward 废、PersonalTrajectory 先修 P0、ContinuousLead 补控件。

2. **`PersonalTrajectoryShader` 的 P0 缺陷（`goal_progress_` 闩锁）**：是先修（保留模块）还是随废弃一起删？
3. **ContinuousLead「追横向移动目标的唯一手段」这个定性需确认**：审查指出这是「补控件优先级」排序的依据，但属事实层未独立复核。若唯一性不成立，补控件优先级应与 PersonalTrajectory 对齐为「先评估再定」。
