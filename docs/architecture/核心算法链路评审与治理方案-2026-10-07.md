### 1.1 ★★ 名为卡尔曼，实为 alpha-beta

`TargetSelector.cpp:264-299` 的真实实现：

```cpp
t.vx += (ncx - t.kx) * g;                              // 速度增量学习
float pos = g + 0.55f; if (pos > 0.9f) pos = 0.9f;
t.kx += (ncx - t.kx) * pos;                            // 位置向观测收缩
t.pred_cx = t.kx + cv(t.vx);                           // 一步外推
```

**无协方差矩阵 P、无卡尔曼增益 K、无矩阵求逆。** 这是教科书 alpha-beta 简化滤波器。

而 `TargetSelector.hpp:122 / 201 / 300` 与 `test_bytetrack_upgrade.cpp` 的注释写着「ByteTrack 卡尔曼」「8 维匀速模型 `[cx,cy,w,h,vx,vy,vw,vh]`」。

**这是"乱"的真实来源之一 —— 代码注释在撒谎。**

## 5. 安全缺陷（实测确认）

### 5.1 NaN 全链路可达

```
NPU 输出含 NaN 位模式（0x7FC00000）
  → DecodeNMS.cpp:79-84  read_elem fp32 memcpy 原样透传，无过滤
  → :270  sigmoid(NaN)=NaN，best *= obj_s ⇒ NaN
  → :272  if (best < conf_thres) continue   ← NaN<x 恒 false ⇒ 不 continue
  → :274-277  x/y/w/h 四趟独立 read_elem ⇒ 全 NaN
  → :279  d.x1 = x - w/2.0f = NaN
  → DetectionBox 坐标即 NaN ⇒ 流入控制链
```

旁证：`DecodeNMS.cpp:47` 的 `half_to_float` 注释**自写「正确处理 denormal/Inf/NaN」**，而调用侧从未过滤。

### 5.2 ★ 三处偶然屏蔽点 —— 解释了"理论可达但从未观测到"

| # | 位置 | 机制 |
|---|---|---|
| ① | `DecodeNMS.cpp:259` `best = -1.0f` + `:264` `if (s > best)` | **NaN 赢不了 max** ⇒ `best` 停在 -1 ⇒ `:272` `-1 < conf` 为真 ⇒ **框被丢在解码层** |
| ② | `TargetSelector.cpp:216` 分数二次过滤 | 与 ① 叠加 |
| ③ | `AimTracker.cpp:8` 首帧 early-return 直通 | 首帧 NaN 被原样吞下 |

**⚠ 这层保护是偶然的（`best` 初值恰好为负数），不是设计出来的。** 任何人改动 `best` 初值或加其他 class 处理，就会暴露。

**坐标 NaN 不经 `best`**，走 `:274-277` 四趟独立读取 ⇒ 这是 N1 的主注入点。

### 5.3 PID NaN 毒化 —— 一个 NaN 帧毒化整个开火期

`Pid1Controller.hpp:92-94` 的防御全是比较型：
```cpp
if (std::abs(error) < 0.3) error = 0.0;              // NaN<0.3 恒 false ⇒ 不归零
if (std::abs(error - last_error) > 30.0) reset();   // NaN>30 恒 false ⇒ 不复位
```
兜底也无效：`:166/:178` 的 `std::clamp(integral_gain, 0.0, 1.0)` —— clamp 定义是 `v<lo ? lo : (hi<v ? hi : v)`，NaN 两个比较都 false ⇒ **返回 v 本身**。

⇒ `integral_gain`/`kp_gain` 永久 NaN，输出永久 NaN。唯一救援是 `reset()`。

### 5.3.1 ★★★【实测】`std::clamp` 与项目私有 `clamp_` 对 NaN 的语义完全相反

这条是本轮最关键的机制发现，**它推翻了"用 clamp 就安全"这一默认直觉**。

实测（WSL g++ `-O2 -std=c++17`，libstdc++，程序在 `.workbuddy/memory/nan_sem.cpp`）：

```
std::clamp(NaN, 0, 1)     = nan          ← 标准：两次比较恒 false ⇒【穿透】
shader_clamp(NaN, 0, 1)   = 1.000000    ← 私有：std::max(lo, std::min(hi,v)) ⇒【吃成上界】
shader_clamp(NaN, -8, 8)  = 8.000000    ← ★对称区间也返回上界，不是 -8
shader_clamp(-inf, 0, 1)  = 0.000000
shader_clamp(+inf, 0, 1)  = 1.000000
std::max(1.0f, NaN)       = 1.000000
std::max(0.0f, NaN)       = 0.000000
std::min(1.0f, NaN)       = 1.000000
```

| 实现 | 源码 | NaN 结果 | 机理|
|---|---|---|---|
| `std::clamp` | libstdc++ `v<lo ? lo : (hi<v ? hi : v)` | **NaN（穿透）** | 两次比较对 NaN 恒 false |
| 私有 `clamp_` | `PersonalTrajectoryShader.hpp:221-223` `std::max(lo, std::min(hi, v))` | **hi（上界）** | `min` 先把 NaN 吃成 hi，`max` 再取 hi |

⚠ **口径纠正**：本文件 §5.3 里"`std::clamp` 对 NaN 返回 v本身"这句**对标准 clamp 成立**，但**不适用于本项目的 shader** —— shader 根本没调 `std::clamp`，它调的是私有 `clamp_`，语义相反。**本项目里"看起来做了钳位"的地方不能假定 NaN 被挡住。**

★ 附带结论：`clamp_` 对 ±Inf 的处理是**完全正确**的（-Inf→lo，+Inf→hi）。**只有 NaN 是病态的** ⇒ 任何用 `clamp_(x, ...)` 当守卫的写法都是**错的守卫**，它把"检测"变成了"洗白"。

### 5.3.2 ★★★【实测】`goal_progress_` 单调闩锁 —— N1 的真P0，优先于所有 NaN 逃逸路径

`PersonalTrajectoryShader.hpp:91-94`：
```cpp
const float measured_progress = 1.0f - err_len / std::max(start_distance_px_, 1.0f);
goal_progress_ = std::max(goal_progress_, clamp_(measured_progress, 0.0f, 1.0f));
const float time_progress = clamp_(elapsed_ms_ / std::max(duration_ms_, 1.0f), 0.0f, 1.0f);
const float progress = std::max(time_progress, goal_progress_ * 0.65f);
```

失效链（每一步都已实测或读码坐实）：
1. `err_len = std::hypot(ex, ey)` = NaN
2. `measured_progress = 1 - NaN/max(...)` = NaN
3. 私有 `clamp_(NaN, 0, 1)` = **1.0**（§5.3.1 实测）
4. `std::max(goal_progress_, 1.0)` = **1.0**
5. `:94 progress ≥ 0.65` 恒成立
6. `skewed_bell_(progress, ...)` 的速度包络**不再随误差收敛而衰减** ⇒ 人形化节奏整段冻结

**不可自愈**：`goal_progress_` 的清零点只有三处 —— `:54`（activate）、`:197`（reset）、`:271`（方向突变）。中间没有任何回落路径（`std::max` 单调）。
⇒ **一帧 NaN，整个交火期间钉死在 1.0。**

★ **为什么这条优先于其余全部 NaN 项**：其他 NaN 缺陷都要"逃到输出"才有害；这条**只要"进来一帧"就成立**，且是**跨帧状态污染** ⇒ 症状表现为"手感变怪"，永远查不到 NaN 头上。这是静默失败的典型形态。

### 5.3.3 `activate()` 的 NaN 洗白（污染源，非产生源）

`PersonalTrajectoryShader.hpp:37`：`const float dist = std::max(1.0f, total_distance_px);`
实测 `std::max(1.0f, NaN) = 1.0f` ⇒ `activate(NaN)` 会把距离当成 **1px**：
- `:45 start_distance_px_ = 1.0` ⇒ 后续所有 progress 计算基数错误
- `:40 index = log2(1/width+1) = 0.1699` ⇒ `duration_ms_` 按"极近距离"算 ⇒ **最激进的包络**

`:270`（方向突变分支）是**二次洗白**，同机制。

⚠ **驳回一条子代理推断**：「`:336` 的钳位会把 NaN 变成 +max_x」。方向对但**路径不可达** ——
`guard_output_f_ :333-337` 的 `max_x = std::abs(raw_x) + cfg.max_extra_px` 由 `raw_x` 推导，`raw_x` 为 NaN 时 `max_x` **也是 NaN**，钳位是 no-op。且 NaN 到不了 `:159`：`adaptive_strength_` 的 `error_factor` 会被 `smoothstep_` 内的 `clamp_(NaN,0,1)=1.0` 压成 0 ⇒ `strength ≡ 0` ⇒ `:134` 守卫恒 false ⇒ `gain = 1.0` ⇒ `out = dx`（有限）。

### 5.3.4 `pull_curve_` 不是 NaN 源，但是 x→y 传播路径（定性纠正）

`PullCurve.hpp:27-34` 的实际路径：
```cpp
const float dist = std::hypot(err_x, err_y);          // NaN
if (dist < cfg.min_distance) return 0.0f;              // NaN < x 恒 false ⇒ 【不早退】
float arc = cfg.strength * std::fabs(out_x) * 0.08f;   // NaN
if (arc > 24.0f) arc = 24.0f;                          // NaN > 24 恒 false ⇒ 【不截断】
const float dir = (out_x >= 0.0f) ? 1.0f : -1.0f;     // NaN >= 0 恒 false ⇒ dir = -1
return arc * dir;                                      // NaN
```

⇒ 结论"不产生 NaN"成立，但**"纯乘法无除法"的理由不成立** —— 代码不做除法不代表 NaN 进不来，它是被**放行**的。
⇒ 真实身份：`AimThread.cpp:537-538` `scaled_y += pull_curve_.apply(..., scaled_x, ...)` ⇒ **x 轴 NaN 的第二条污染路径（→ y 轴）**。

### 5.3.5 N1 范围口径：产生源 vs 污染源

原提议"NaN 产生源从 3 个降到 1 个，测试矩阵收窄到 2 行" —— **不成立**。区分：

|---|---|---|---|
| `DecodeNMS.cpp:274-284` | ✅ 是（主注入点） | — | 必须 |
| `PullCurve.hpp:27-34` | ❌ | ✅ x→y 传播 | 必须 |

| `PersonalTrajectoryShader::shape_f` | ❌ | ✅ `goal_progress_` 闩锁 | **必须（优先级最高）** |

⇒ N1 目标是"阻断污染"，不是"消灭产生"，两轴都要覆盖。**测试矩阵维持 4 行维度。**

### 5.4 ★★ NaN 测试是假的

`core/tests/test_pipeline.cpp:148-162` 的 `test_nan_inf()` 注释写「NaN/Inf → 必须拒绝」，但：

### 5.8 ★ `copysign` 缺陷：`kHidMin` 侧恒差 1（实测）

`AimThread.cpp:742-746`：
```cpp
constexpr float kHidMax =  32767.0f;
constexpr float kHidMin = -32768.0f;
const float cx_f = std::clamp(emit_x, kHidMin, kHidMax);
...
move_x = static_cast<int16_t>(cx_f);
```

实测（`.workbuddy/memory/copysign_probe.cpp`）：
```
clamp(-40000, -32768, 32767) = -32768.000000
  copysign(1.0f, -32768.0f)  = -1
clamp(+40000, -32768, 32767) =  32767.000000
  copysign(1.0f, +32767.0f)  = +1
```

⚠ **口径纠正**（子代理原报「转 uint8 得 255」是**视角错误**）：HID 报告字段是 `int16_t`，`-32768` 是**合法值**，`copysign(1.0f, -32768.0f) = -1` 是**数学正确**的。
⇒ 真实缺陷是：**负向饱和时钳位值恰为 `copysign` 的边界哨兵**，任何形如 `if (copysign(1.0f, v) == -1) 归零` 或 `abs(v)==kHidMin` 的下游判据都会误判。
⇒ **本身不是 UB，也不是 HID 越界**（`-32768` 正好在 int16 范围内）。是**判据脆弱性**，定级 P2 而非 P1。
★ 修法：`kHidMin` 改 `-32767.0f`（对称留一），或在所有 `copysign` 判据处避开边界哨兵。**需先查是否有下游依赖 `-32768`。**

### 5.9 `Pid1Controller` 毒化的持续性 —— reset() 能救，但只对「error 恢复为有限」成立

**实测**（`.workbuddy/memory/pid_reset_probe.cpp`，参数取自 `:223 integral_gain_threshold=50.0`、`:224 integral_gain_rate=0.025`）：

| 场景 | 实测结果 |
|---|---|
| error 有限（0.5）但被污染 NaN，500 帧后 | `integral_gain = nan` |
| `reset()` 后 | **精确归零 0.000000** ✅ |
| 再喂 1 帧有限 error | `0.024750`（开始重建） |
| 再喂 500 帧有限 error | `0.989997`（爬升，**不是回到原稳态**） |
| **`reset()` 后 error 仍持续 NaN，500 帧** | **再次变 `nan`** ❌ |

⇒ **两条结论**：
1. `reset()` **能**把毒化清干净（§5.3 的"永久 NaN"需修正为"**error 恢复有限后 reset 可自愈**"）
2. ★ **但 `reset()` 挡不住持续 NaN** ⇒ **必须靠入口守卫**，不能指望 reset 兜底

⚠ **同时推翻一条验收判据**（子代理自查发现的苗头，我实测确认）：
「灌 500 帧 NaN → reset → 再灌 500 帧 ⇒ 与全新实例逐位相同」**不成立** —— 爬升速率由 `integral_gain_rate=0.025` 决定，收敛需要时间。
⇒ 验收必须写成**「reset 后 N 帧内与全新实例偏差 < X%」**，不能写"相同"。
⇒ 这是 §10.2「回放只能验证有限值」之外的**第二条**验收纪律：**加守卫后的恢复路径必须单独定判据，不能沿用"跑够帧数即恢复"的直觉。**

## 10. 附：方法论沉淀

### 10.1 本次协作的三条教训

1. **业主提出技术判断时禁止直接附和** —— 业主说"卡尔曼是辅助"，实测是"**它已经是了，而且它连卡尔曼都不是**"。直接附和会同时错两次。
2. **转述他人结论必须标出处** —— 本次出现 3 次出处错标（`AimError.hpp` 零引用被归给 team-lead 实测，实为架构师查；`HidForwarder` 缺陷未标并发组；`has_objectness` 两人独立犯同一个反向推理错误）。**自认注释 ≠ 实测验证。**
3. **「测试替身 ≠ 生产对象」已是第二例** —— `TestPidController` 与 `pixel_error` 两种形态。现有门禁 G1-G7 **没有一条能发现这类问题**（它们查行数、空 catch、路径、标记一致性）。

### 10.2 批次纪律（已冻结）

| 纪律 | 内容 |
|---|---|
| **回放只能验证有限值** | 加 isfinite 守卫后回放必然逐帧 bit-exact ⇒ **门禁全绿 + 回放通过但行为已变且无人知晓**。验收口径：**「没被测到 ≠ 没发生」** |
| **混装必假绿** | 「搬运」与「加守卫」不得同批 —— 混装后无法区分"是搬错了还是守卫改变了行为" |
