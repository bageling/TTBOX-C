# 自瞄「算」链路改造方案 · 像素域标定（2026-10-07）

> 决策人：业主。路线：**纯视觉（不读游戏内存）** + **每个新游戏第一次跑一次标定** + **删除 fov_mode 半成品**。

---

## 0. 为什么是标定，而不是「角度域」（带调研证据）

### 0.1 曾经的假设（已推翻）

曾认为「3D 游戏控制对象是角度，应把 PID 搬到角度域（atan 换算）」。经 7 个 GitHub 项目 + 2 个业主提供源码核查，**该假设不成立**：

| 项目 | 闭环域 | FOV/角度 |
|---|---|---|
| SunOner/sunone_aimbot（最火） | 像素 | 有 `mouse_fov_*` 参数，但当"旋钮"凑（默认 40，非真实 FOV） |
| **BB-828（业主提供，5386 行）** | **像素** | **fov 命中 = 0** |
| **yey（业主提供，2498 行）** | **像素** | **fov 命中 = 0** |
| RootKit-Org/AI-Aimbot | 像素 | 无（`aaMovementAmp=0.4`） |
| yan77-h/AimBot | 像素 | 无（`smooth=0.8`） |
| sokopo6/CS2_External（DMA） | 角度 | 读内存直接算 `Yaw=atan2(dy,dx)` |

**结论**：除「读游戏内存」（DMA/CS2 External）外，**全部主流纯视觉方案都是像素域闭环**。yey 里 4 处 `atan` 全用于贝塞尔曲线分段插值，与 FOV 换算无关。

### 0.2 纯视觉的物理天花板

纯视觉拿不到「视角角度」与「游戏 FOV」，因此 `π/FOV/焦距` 这一层**无法被真实测量**。`FovAngle.hpp` 里的 `atan(err/焦距)` 因焦距是假参数而**不代表更正确**——它缺真实 FOV 输入。

⇒ 唯一可行路线：**保持像素域闭环，把揉进 `kp` 的隐含系数显式化为可标定量**。

## 1. 要解决的问题

现状（`AimThread.cpp` 误差段）：

```
像素误差 err_px  →  kp × err_px  →  count
```

`kp` 把三件事揉成一个数：
1. 目标在画面里的**几何放大率**（离准星远近的视觉比例）
2. **游戏灵敏度**（count → 视角角度）
3. **游戏 FOV**（视角角度 → 画面比例）

⇒ 换游戏 / 换 FOV / 换灵敏度 ⇒ 必须重调 `kp`。这就是「理论强、上真机就飘」的**真实根因**（不是缺 atan）。

## 1.5 对标补充：BB-828 的四个「自适应」机制（2026-10-07 深度分析后新增）

详见 `docs/architecture/BB-828深度分析报告-2026-10-07.md`（5386 行全文分析，结论附行号）。

BB-828 与我们**架构同构**（像素域闭环、FOV 命中 0），但它有**四个我们没有的「按框尺寸/速度自适应」机制**
—— 这是纯视觉方案能做的物理补偿，比"角度域"更实际：

| 机制 | BB-828 源码 | 效果 | 我们的差距 |
|---|---|---|---|
| **框面积 → 选靶范围** | `:4576-4582` `calculateDynamicRangeValue` | 远小目标(≤200px²)用小范围 40px；近大目标(≥1200px²)用全范围 100px；中间线性插值 | ❌ 固定 `search_radius_px` |
| **框面积 → 滤波强度** | `:1806-1817` `getDynamicFilterMin` | 小目标强滤波、大目标弱滤波 | ⚠ 已有 `box_adaptive`，但只驱动 One-Euro 截止频率，未用于死区/门控 |
| **速度 → Kp 双档** | `:1759-1775` `getSpeedAdaptiveKpMultiplier` | 帧间位移≥阈值 ⇒ 提高增益；静止 ⇒ 降低增益 | ❌ 无 |
| **Y 轴提前量抑制** | `:1830-1840` | `\|lastMoveY\|` 超阈值 ⇒ 提前量归零，防纵向抖动被放大 | ❌ `continuous_lead` 无此机制 |

**另有 `auto_tuning`（`:4725-4748`）只测量打印、不自动改参** —— 我们把它接进二分搜索即可自动化（见 2.1/2.2）。

★ BB-828 两处缺陷我们无、不必照抄：`:889` 返回 `distance²` 而 `:885` 返回 `distance`（量纲不一致）；
`sizeScore = 面积/10000` 在 640 窗口下 2 倍镜起全部撞顶（我们 V3 阶段 4 已改为 `sqrt(面积)/size_ref`）。

## 2. 方案：闭环可观测标定（照 BB-828 `auto_tuning` 范式）

### 2.1 核心洞察

不需要知道 FOV 或角度。**用闭环的可观测指标反推系数**，全部只依赖像素：

| 指标 | 判据（BB-828 `:4725-4748` 源码） | 含义 |
|---|---|---|
| **过冲次数** | 误差符号变号次数 | 增益过高（冲过头）的直接证据 |
| **响应时间** | 首次锁定 → `absError < 10px` | 增益过低（追不上）的证据 |
| **稳定时间** | 首次锁定 → `absError < 5px` | 收敛快慢 |
| **峰值误差 / 平均误差** | `max / Σ\|err\|/n` | 抖动量 |

### 2.2 标定算法（二分搜索 kp）

```
输入：目标（游戏 + 灵敏度）、时长 T（默认 5s，对齐 BB-828 的 detect_time=3~5s）
1. kp ← 当前值，区间 [kp_lo, kp_hi]（建议 1.0 ~ 25.0，板端已验 12 附近可用）
2. 采样 T 秒，记录：overshoot_count / settle_time / avg_error
3. 判定（依据板端 V1.0.40 实测的失稳机理：延迟 48.9ms × 单帧峰值 × 144fps ⇒ 冲过头 ~180px > 裁剪半宽 320px 的同类教训）：
   · overshoot_count > 阈值(建议 2)  → 增益过大 → kp_hi = kp，kp ← (kp_lo+kp)/2
   · settle_time > 阈值 或 未收敛     → 增益过小 → kp_lo = kp，kp ← (kp_hi+kp)/2
4. 收敛条件（满足其一即停，避免无意义迭代）：
   · |kp_hi - kp_lo| < 0.1
   · 迭代次数 ≥ 8（上限，防止耗时失控）
5. 落盘 kp 到 config.d，标注游戏名
```

**每轮需重置 PID**（对齐 AimThread 现有 `pid_x_.reset()` / `pid_y_.reset()` 语义）。

### 2.3 为什么不用 atan / 角度域

- 标定出的 `kp` 是**等效系数**，已包含该游戏的全部隐含关系；
- 引入假 FOV 只会增加一个需要人填、且填错就出错的参数 ⇒ 净增复杂度、净减可靠性。

## 5. 验证方法（铁律：无证据不写 PASS）

1. **离线**：用 `core/tools/replay/ttbox_replay` 喂已知 kp 的合成轨迹，验证 `AimTuner` 能收敛到真值。
2. **板端**：手动跑一次标定，对比标定出的 kp 与手动试出来的 kp（板端已知 12 可用）。
3. **回归**：ctest + pytest 全绿；口径门禁 PASS。

## 6. 风险

| 风险 | 缓解 |
|---|---|
| 标定期间准星乱飘（会打到人） | 标定必须走 `calibrating` 旁路 + 提示用户「找空地/训练场」；建议加一个「只采样不输出」模式 |
| 目标不稳定导致判定失真 | 判定要求「持续存在同一目标」，否则本轮作废重来 |
| 标定耗时过长 | 单轮 ≤5s，上限 8 轮 ⇒ 最坏 ~40s；面板显示进度 |
| 游戏 FOV 不可见 | 不需要，只需同一游戏同一灵敏度下跑一次 |
