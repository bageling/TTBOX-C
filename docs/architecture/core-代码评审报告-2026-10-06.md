## 0. 结论速览

- **语言构成：C++ 绝对主导。** 自有代码 100,838 行中，C++（`.cpp`+`.hpp`+C 头）合计 **67.3%**；前端 JS/CSS/HTML 合计 15.6%；Shell 9.3%；Python 7.5%。

- **标准：维持 C++17 不动**（两派实质一致；GCC 12 对 C++20 库特性不全，且无任何被 C++17 挡住的需求）。

## 3. 评审发现（四路专项）

### 3.1 标准用法（史准通）

**总体**：健康度很高，**无 P0**。裸 `new/delete` 近乎绝迹（唯一一处 `WebServer.cpp:116` 是 httplib 线程池 API 契约），`enum class`/`override`/虚析构/默认成员初始化器/`#pragma once` 全部到位。

| 严重度 | 位置 | 问题 |
|---|---|---|
| **P1** | `common/Json.cpp:89-93` | `as_int` 浮点→`int64_t` 转换**只挡了 NaN/Inf，未挡有限值越界**，属标准 UB；JSON 数字可为 `1e300`，经 web 请求体/`SET_CONFIG` 深合并即可触发（GCC/Clang 实测饱和为 `INT64_MIN`，但不可依赖） |
| P2 | `rknn/DecodeNMS.cpp:79,86,89,92` | `reinterpret_cast` 类型双关读 `float`/`int16_t` ⇒ 严格别名违规；**同文件 `:71/:82` 已用合法的 `memcpy`**，写法自相矛盾 |
| P2 | `mouse/MouseRouter.cpp:29-31` | `buttons_size` 未校验 ≤4 即 `<< (8u*i)`，移位 ≥32 是 UB（该文件**全仓无生产调用方**，注释自承） |
| P2 | 全仓 | `[[nodiscard]]` **0 处**（4.2 万行、大量 `bool f(..., std::string* error)` 失败返回式接口）；`std::string_view` **0 处**；`std::optional` 仅 3 个文件 |
| P2 | `common/Json.cpp:156,179,461` | 用 locale 敏感的 `strtod`/`snprintf("%.9g")` 而非 `from_chars`/`to_chars`（若进程切到 `de_DE` 等 locale，`1.5` 会被解析错） |
| P2 | `common/Json.hpp:53-60` | 手写标签联合（6 个成员全量常驻）替代 `std::variant`，每个 JsonValue 恒占一个 string+vector+map 的空壳体量 |
| P2 | `input/PhysicalMouseReader.cpp:146`、`runtime/HardwareRunner.cpp:20` | **压缩(minify)风格**，单行 400+ 字符（全仓 `awk length>300` 仅命中这两文件），而 `HardwareRunner` 恰是核心生命周期 |
| P2 | `web/domain/hardware.cpp:41,60` 等 | `atoi/atof/sscanf` 无错误反馈（`atoi("abc")==0` 与真实 0 无法区分） |
| P2 | `mouse/TargetSelector.hpp:169` | 全仓唯一非 `enum class` 裸枚举；另有 20+ 文件手写 `(void)x;` 而非 `[[maybe_unused]]` |

**亮点**：所有权纪律到位（`shared_ptr<uint8_t[]>`、`unique_ptr`、`=delete` 12+ 处）；10/10 多态基类有虚析构；**141/141 头文件 `#pragma once`**；`using namespace` 0 处；浮点域层层 `isfinite`/`clamp` 设防（`FittsAimController.hpp:63-66`、`AimThread.cpp:780-787`）；JSON 解析器有 RAII 递归深度护栏（`Json.cpp:251-265`，kMaxDepth=256）；真用上 C++17（`filesystem`/结构化绑定/`clamp`/`optional`/`if` 初始化/`scoped_lock`）。

**关闭/取消语义评估（含新发现的缺口）**：

- **缺口（新）**：`SO_RCVTIMEO/SNDTIMEO` **只约束卡在 recv/send 的线程，不约束 handler 本身**。实际下界 = 最长在途 handler：RUNTIME_CONTROL ~1–2s、MODEL_ACTIVATE ~10s、**`HARDWARE_ACTION`（APPLY_EDID/SET_USB_MODE，`IpcServer.cpp:752`）经脚本/systemctl 执行、潜在无界** ⇒ **脚本挂住则 `Application::shutdown()`（先调 `ipc_.stop()`，`Application.cpp:958`）永久退不出**。已确认**无自死锁**（shutdown 仅主线程调用）；不建议 detach 改 join；根治 = `shared_ptr` + `enable_shared_from_this`。

### 3.4 热路径性能（费敏杰）

**总体**：链路是**认真的低延迟设计** —— V4L2 mmap + dma-buf → RGA 常驻 DMA-BUF（缓存 import 句柄）→ RKNN 输入 DMA-BUF 直绑，**全程无 CPU 大图 memcpy**，`xor_shift128_copy` 已 NEON 向量化。判断不以"CPU 饱和"立论（板端实测 core CPU 仅 23.3%、RSS 174MB，有 4 倍余量）—— **对实时瞄准设备，核心指标是延迟与抖动（尾延迟）**。

| 严重度 | 位置 | 问题 | 预估收益 |
|---|---|---|---|
| **P0** | `runtime/CoreRuntime.cpp:196` + `aim/AimThread.cpp:83,1061` | AimThread 以 **4000µs 非阻塞轮询**取帧（`take_latest` 无阻塞原语，取不到即 `sleep_for(interval_us_)`），worker 发布后最多要等 ~4ms 才进 PID | 减少核心链路 publication→PID 的量化延迟（均值 ~2ms、尾 4ms）；**需实测** |
| P1 | `rknn/DecodeNMS.cpp:244-256,389-400` | 每帧对**全部 anchor × 全部类别**做 argmax 扫描（conf 过滤前），`read_elem` 每元素一次类型 switch，FP16 走 `half_to_float` denormal 循环；单输出 `(1,84,8400)` ⇒ 每帧 ~7×10⁵ 次 `read_elem` | decode 在 NPU 之后的关键段；**需先看 `decode_ms` p50/p95** |
| P1 | `capture/V4L2Capture.cpp:706,732-736,746-755` | 采集线程**每帧 2 次堆分配**（`make_shared<FrameBuffer>()` + `plane_lengths_of()` 返回 `vector<size_t>` 按值，而 `num_planes≤8` 已在 `:383` 校验） | 降分配器抖动；微秒级、置信度中 |
| P2 | `DecodeNMS.cpp:288-301` 等 | classwise 分组 O(k²) + 每类全量扫；`nms_boxes` 每次分配 `order/removed` | 低（`cands_` 已过滤，规模通常数十） |
| P2 | `DecodeNMS.cpp:317,459,557,720,789` | `*detections = kept_;` 每帧整段拷贝 | 低（容量常够复用） |
| P2 | `mouse/TargetSelector.cpp:167,212-223,281` | `collect_candidates` 按值返回；`looks_like_round_object` O(n²)；`trim_tracks` 超限时每帧 `stable_sort` | 低（FOV 内候选个位数） |

## 4. 裁决（狄明断）

### 4.1 裁决总纲

> **采纳稳健派为骨架，但把它漏掉/降档的三条正确性项提到随批**：立即修只认"**真缺陷**"四条（A1–A4，含 2 个 P0 数据竞争）；随批带上零成本安全网（含 `Stats::scoped_lock`、`MouseRouter` 校验、`V4L2Capture final`、健康量原子化、aim 阶段计时）；其余一律"暂缓 + 明确触发条件"或"明确不动"。**全程三步、一次上板搞定，回滚限单文件。** 标准维持 C++17。

判据：正确性/安全性一票通过（数据竞争、UB）。共 4 条，**全部单文件可 revert**。

### 4.7 六、修复顺序与验收（分步 + gate + 回滚）

> 关键设计：**唯一一次上板同时产出「基线数据 + 修复验证 + 新增 aim 仪表数据」。**

- **Step 0 · 冻结基线（同一上板 session 的前半段）**：在运行中的 V1.0.61 上先读面板 `decode_ms / decode_p50/95/99`、`e2e_p50/95/99`、`infer_ms`、`fps`、`CPU%`、`RSS` 并归档。
  **Gate0**：数据成功读取并归档 —— **若读不到，不得烧修复批次**。
- **Step 1 · 必改批次（A1–A4 + 随批 B1–B7）**：编译 → 单测 → 离线回放/soak → 板端验证。
  **Gate1**：① 零**新增**告警；② 单测全过；③ 离线回放/soak 无回归；④ 板端开 `pid_trace` 正常落盘；⑤ 面板 `last_dequeued_count` 稳定、`aim_ms/p50/p95` 非 0。
  **回滚**：A/B 类均单文件、无跨文件签名变更 ⇒ `git revert <commit>`。
- **Step 2 · 读数据判性能（纯读，不烧板）**：读 `aim_ms/p50/p95` + `decode_ms/p95` + `e2e_p95/p99`。
  **Gate2**：**只有到这一步、且尾延迟显示实际瓶颈，才允许讨论 C1 性能重构**；否则关闭性能议题。
- **Step 3 · 有条件重构（仅当 Gate2 触发）**：先补离线回放测试再动结构。
  **Gate3**：结构化改动必须有回放对照（逐位/统计等价）。

**回滚总纲**：A/B 类全部单文件、无跨文件签名变更 ⇒ `git revert <commit>`。这正是裁决人否决"改 `start()` 签名"版的根本原因 —— 跨文件签名变更会破坏该总纲。

## 5. 遗留待业主决策（必须拍板）

1. **`HARDWARE_ACTION` 脚本超时（`IpcServer.cpp:752`）**：脚本/systemctl 潜在无界 ⇒ 脚本挂住则 `Application::shutdown()` 永久退不出（**关机/重启会卡死**）。**选项**：(a) 硬化 —— `shared_ptr`+`enable_shared_from_this`（需把 `Application.hpp:164` 按值 `IpcServer ipc_;` 改 shared_ptr）+ handler 超时；(b) 运维约束 —— 要求脚本自带限时。**涉及关机安全性，需业主选。**
2. **web 是否独立发布**：决定 C4（web/core 分离、单一静态库拆分）的优先级。若不独立发布，C4 可长期不动。
3. **`decode_ms` 端到端现状核实**：代码已证有产出，但**板端面板显示值**需在 Step0 确认非 0；若为 0 ⇒ 上游统计吸收点断线，需单独排查。
4. **一次上板窗口安排**：必须同一 session 内**先采基线、后烧修复批次**，否则拿不到修复前基线。
5. **B1 落盘路径/权限**：aim 阶段 trace/计时在板端的落盘位置与 root 权限确认。

## 附录 · 评审方法与证据链

- **流程**：Workflow A（代码评审）—— Phase 1 四路专项并行（标准/架构/并发/性能）→ Phase 2 现代派 vs 稳健派分别出方案 → 独立裁决人综合裁决。
- **交叉校正（团队流程的实际价值）**：
  1. 性能侧纠正了架构侧"改用 `atomic<shared_ptr>` 即真无锁"的错误说法（libstdc++ 上仍为锁实现），架构侧已认错并作废该建议。
  2. 并发侧与性能侧共同纠正了"`AimThread` 是 RT 线程"的误判（`AimThread.cpp:74-81` 只绑核、无 `RtSched::apply_fifo`），#7 由"RT 优先级反转"更正为"CFS 下的可控尾延迟"。
  3. 并发侧精确化了 IpcServer 关闭语义（`SO_RCVTIMEO` 不约束 handler），并否定了"detach 改 join"的方向。
  4. 稳健派核实了"`decode_ms` 其实已在测"，纠正了性能侧"需先测"的表述。
- **约束**：全程静态只读；未上板、未编译、未运行测试。凡涉及运行期量级（延迟、占空比、竞争窗口）的结论，均由分析者显式标注"需实测"，本报告保留该标注。
- **证据索引**：所有结论均可由文中的 `文件:行号` 在原仓复核；语言占比脚本口径为 `git ls-files` + 非空行计数（可复现）。
