## ★★★ 核心发现 1：板端 PID 在跑一个「不可能是人类行为」的形状

实测（`.workbuddy/memory/pid_human_probe.cpp`，板端实测参数 kp=25 kd=25 smooth=9900 gain=0.65 predict=0）：

### 1a. 积分项被 `predict` 门控到恒为 0 ⇒ 系统退化成纯 P+D
`Pid1Controller.hpp`：`ki_raw = (ki_raw * predict) * integral_gain;`
板端 `predict_x=0, predict_y=0` ⇒ **`K_i ≡ 0`**，两轴都只剩 P+D。
- **P+D 的物理含义**：输出 ∝ 当前误差。误差大 → 猛拉；误差小 → 慢挪。
- **人类的缺失**：真人瞄准有「累积体感」——看到偏了会整体压过去，而不只是按当前误差线性退让。
- **症状对应**：记忆里已记「X 缺 I ⇒ 拉不住静态横偏」「Y 缺 I ⇒ 补不了后坐力斜坡」——从行为角度看，是**系统不会「攒」修正量**。

### 1b. `smooth=9900` 把 P/D 项压到 **0.5%~1%**（smoothTerm 软限幅实测）
| 误差 | Kp_raw | 经 smoothTerm | 实际放大 |
|---|---|---|---|
| 10px | 250 | 2.50 | **0.0100** |
| 50px | 1250 | 12.17 | **0.0097** |
| 100px | 2500 | 22.59 | **0.0090** |
| 300px | 7500 | 40.59 | **0.0054** |
- `smoothTerm` 的 `outputScale = bandwidth - smooth = 100`，而分子分母的比值在 ratio≪1 时趋近 1 ⇒ **整个 P/D 项乘以约 0.01**。
- **人类逻辑**：这意味着「面板上 kp=25，实际有效比例增益只有 0.25」。**面板在骗业主**——他调 kp 从 25 到 50，行为只变 2 倍不到；调 smooth 从 9900 到 9950，行为变 5 倍。**两个旋钮的作用量级完全不对等，但面板把它们平铺在一起。**

### 1c. 输出时间序列是「单调收敛、永不过冲」的机器曲线
实测帧序列（predict=0，目标 300px）：
```
帧0 误差300 → 步长52.8px
帧1 误差247 → 步长16.8px   （已减速）
帧2~23 误差230→14，步长平滑递减 21.8→1.9px
符号翻转次数 = 0     最终误差 1.17px（进 deadzone 归零）
```
对照 `predict=1`（仓库出厂值）：符号翻转 **2 次**、最终误差 0.32px——**有轻微过冲、像点人味**。

**★ 人类行为 vs 机器行为的核心差异**：

| 特征 | 真人打目标 | 板端现状（predict=0） |
|---|---|---|
| 起步 | 爆发、快 | 爆发（52px/帧）✓ |
| 接近时 | 明显减速、微调 | 平滑减速 ✓ |
| **到位瞬间** | **小幅过冲（overshoot）** | **永不过冲** ✗ |
| **回拉修正** | **有**（人的微调本能） | **无**（单调收敛）✗ |
| 抖动 | 手部自然噪声 | 无噪声（除非开拟人化）✗ |
| 感知 | — | **像"云台自动对位"，不像人手** |

**人类逻辑判据**：真人**几乎不会**一次到位且零过冲——神经肌肉的过冲是普遍现象。一条永不过冲的追踪曲线，在行为上就是「机器」。

## ★★★ 核心发现 2：`predict` 的语义是「输出自激励」，不是「预测」

`Pid1Controller.hpp`：`target_velocity = error_diff + last_u * gain;`
然后 `ki_raw = raw_velocity_input * predict`。

- `last_u` 是**上一帧自己的输出**。所以 `predict` 越大，输出越被自己放大 ⇒ **自激励**。
- 记忆里已记：有效增益 ≈ `1/(1−0.667·predict)`。predict 逼近 1.5 时爆炸 ⇒ 业主之前的「飞出去」正是这个。
- **人类逻辑**：一个「预测」参数，本该是根据目标**运动趋势**预测未来位置；这里是**把自己的输出当反馈放大**。名字与实际行为不符 ⇒ **业主调这个参数时，他的直觉模型是错的**。

## ★★★ 发现 6：参数「名字骗人」清单（chain-coupling 审计 + 主理人复核）

| 参数 | 面板标签 | **实际作用** | 危害 |
|---|---|---|---|
| `smooth` | 「缓冲」 | **削弱倍率** `10000−smooth`。越大输出越弱 | ★★ 调"更稳"反而输出砍到 1/10 |
| `rate` | 「跟随速度」 | `kp_gain` 的**爬升速率**，不是平滑率 | 调大 = 更凶 |
| `predict` | 「预判」 | **输出自激励前馈**（`last_u*gain`） | ★★ 当"预测"调会发散 |
| `output_deadzone` | 「小于它就不动」 | **余数累积**，决定"多久发一次" | 余数一直保留，没被丢 |
| `fov_range` | — | **零消费死字段**（真正生效的是 `fov.radius`） | 改了没反应 |
| `deadzone_x/y`、`OutputScale`、`RateLimiter` | — | **生产零 include**（仅测试用） | 看着像安全兜底，其实没有 |

### ★★ 两条最危险的
1. **`smooth=0` ⇒ 整个软限幅块被 `if(smooth)` 跳过 ⇒ 输出暴涨 100 倍**
   （`Pid1Controller.hpp:120`）。面板滑杆范围 `[0,9999]`，**0 就在最左边**，而 `RuntimeProfile` 只校验上界。
   ⇒ 出厂注释自述「之前恒传 0.0 等于把最重要的一道大误差保护整个关掉」——**V1.0.13~V1.0.37 业主一直是在这层保护全关的状态下调参的**。
2. **`predict` 无任何范围上限校验**（`RuntimeProfile.cpp:172-189` 只校 kd/kp/smooth/rate），而面板允许填到 **10** ⇒ 回路上溢发散。

## ★★★ 发现 7：实战失效模式（chain-practice，与业主历史症状逐条对上）

### 7a. `trim_tracks` 排序方向反了（**删最健康的、留最陈旧的**）
`TargetSelector.cpp:286-295`：comparator 把「丢失多/更早未见」排**前**，`pop_back()` 删**尾**
⇒ 优先删「刚丢的新鲜轨迹」，把「僵尸」留下持续参与关联竞争。
- **实战体感**：切目标后短暂"失灵"，要等很久才重新咬上；多目标场景下"跳着打"。
- **修法**：`pop_back()` → `erase(begin())`，或反转两处比较方向。**改动极小、收益大。**

### 7b. `lost_frames` 冻结 ⇒ 第一个 `trim_tracks` 删除条件**永不成立**
三处 `lost_frames++` 都在 `if(t.active)` 内（`:235/:380/:522`）⇒ 非激活轨迹计数冻结
⇒ 删除条件 `!active && lost_frames>buffer` 永假 ⇒ **全靠 `max_tracks` 那条 pop_back 兜底**
⇒ 与 7a 叠加：**先删新鲜的、僵尸全留着**。
★ 定档案里记的是 `:240/:307/:412`，实际现在是 `:235/:380/:522`——**已被后续改动漂移，按符号查别按行号。**

### 7c. ★ 「越打越慢」：输出相位滞后随稳态误差累积
`Pid1Controller.hpp:218-234` 的速度观测器：`Ki` 随误差增长 ⇒ 速度估计滞后**越来越长**
⇒ 静止瞄准的输出**比移动目标慢** ⇒ 业主追静止点会觉得"跟不动/糊"。
★ **这可能是「跟手度不足」的物理主因**，比调 kp 更本质。

### 7d. `sm == off_deadzone` 时位移被完全丢弃
`AimThread.cpp:735-742`：门限判断用 `>=`，正好相等时**丢进黑洞**（本帧剩余量被 rem_ 吸收）
⇒ 静止时最后几个 count 永远发不出去 ⇒ 微调"差最后一丢"。

### 7e. 「突然一大跳」的三个源头
`preserve_direction`（`AimThread.cpp:474-477`）死区回放 / `boost_until` 非原子 / `while(true)+sleep(1ms)` 的节拍器（20 拍 ≈ 21ms/拍）。

### 7f. ★ 出厂配置把「落点修复」的前置全关掉了
V1.0.41 修「近身落点上飘」的**两个前提**：
① 动态选靶范围（依赖 `search_radius_px`）—— 出厂 `fov.enabled=false, radius=1` ⇒ **`fov_range` 公式退化成 1** ⇒ 半径恒为基准值（限幅失效）
② `capture` 320×320 —— 记忆实测板端曾为 **640×640** ⇒ **有效裁剪区不同** ⇒ 同一个 `offset_y` 在不同 capture 下含义不同。
⇒ **业主"没配好"的体感，可能出厂就带着。**

## ★★★ 发现 9：★「准星莫名向上一跳」的直接成因（chain-coupling 发现，主理人已核实）

`PullCurve.hpp:24-37` + 出厂配置（`10-device.json`：`pull_curve.enabled=true, min_distance=80, strength=0.8`）：

```cpp
float arc = cfg.strength * std::fabs(out_x) * 0.08f;
if (arc > 24.0f) arc = 24.0f;
const float dir = (out_x >= 0.0f) ? 1.0f : -1.0f;   // ★ out_x==0 也判为 +1
return arc * dir;
```

**★ 核心缺陷**：`out_x == 0.0f`（X 恰好不动的那一帧）时，`dir` 仍判为 `+1`
⇒ **注入 +24 count 的纯 Y 偏移，而 X 完全不动** ⇒ 准星凭空向上跳一下。
- 触发门槛 `hypot(err) ≥ 80px`（**出厂就是 80**，误差一大就在触发）。
- `|out_x| ≥ 375` 时撞 ±24 硬顶 ⇒ **X 误差越大，Y 阶跃越大，直到饱和**。
- 该偏移进 `scaled_y`（`AimThread.cpp:505`），位置在 `remainder` 累加**之前** ⇒ 被 int16 量化放大成可见的一跳。
- **面板完全看不出来**（只有一个「拉枪曲线」开关，不提会注入垂直偏移）。

**⇒ 这就是业主主诉「打完向右上角拉一下」+「准星莫名向上一跳」的最直接成因。**

**修法（3 选 1，建议 ③）**：
① 出厂 `pull_curve.enabled` 改 `false`（1 行，但业主可能正用着拉枪）
② 面板 hint 明写「会在 X 拉枪时注入 Y 偏移」（0 风险，但治不了）
③ **`PullCurve.hpp:34` 加零位移短路**：`if (std::fabs(out_x) < 1.0f) return 0.0f;`（治本，且不改变正常拉枪行为）
