# TTBOX web 层结构优化方案（后端 + 面板双拆）

> 日期：2026-10-02 | 状态：**Proposed**（待业主批准后执行）
> 基线：`bin/ttbox-web.py` 3645 行 / `lib/` 21 模块 4081 行 / `templates/index.html` 13446 行

---

## 0. 为什么要做（问题陈述）

现状实测：

| 指标 | 数值 | 问题 |
| --- | --- | --- |
| 入口行数 | 3645 | 89 个路由/钩子 + 60 个函数 + 100 条顶层语句挤在一个文件 |
| Flask app | 单点实例化 | 无工厂、无 Blueprint、无注册表 |
| 可插拔机制 | **0 处** | `register` / `plugin` / `entry_point` / `Blueprint` / `importlib` 全命中 0 行 |
| lib→入口耦合 | 37 处 `hub.call` | lib 无法脱离 Flask app 独立运行 |
| 面板单文件 | 13446 行 | CSS 5188 + JS 7219 + HTML 1030，396 个顶层 JS 符号 |
| 超 300 行文件 | 4 个已登记 | calibration 795 / profile_translate 623 / branding 396 / state_snapshot 365 |

★**路由数复核**：精确数是 **89 个**（GET 31 / POST 38 / PUT 9 / DELETE 6 / PATCH 2 = 86 路由
+ 1 `before_request` + 2 `errorhandler`）。此前口头说的「90」多算了 1 个。
快照已落`scripts/web_route_snapshot.txt`（89 条，附文件头）。

**核心问题**：模块化做了（`lib/` 21 个模块、依赖无环），但**可插拔性为零**。
加功能必须改入口那个大文件，摘功能只能注释路由。这不是"文件太长"，是**架构没有扩展点**。

**这个方案要解决两件事**：
1. 后端：入口收到 < 250 行，路由按域切 14 个 Blueprint，建立 app 工厂
2. 前端：面板从单文件 13446 拆成模板 + 静态资源

## 2. 后端方案

### 2.1 路由分域（89 个 → 14 个文件）

按实测路由表分域，**URL 前缀一字不改**：

| 域文件 | 路由数 | 行数 | 覆盖 |
| --- | --- | --- | --- |
| `models.py` | 18 | ~340 | list/import/onnx/select/delete/concurrency/class_names/pipeline_depth/remote_frame_format |
| `aim.py` | 12 | ~180 | 压枪配置 + 档位 + hotkey guard |
| `motion.py` | 11 | ~80 | profile CRUD + training session |
| `system.py` | 8 | ~50 | hostname / web_port / reboot / poweroff / storage expand |
| `license.py` | 6 | ~150 | activate / reactivate / gate / full_recovery |
| `calib.py` | 6 | ~90 | auto_calibration 生命周期 + amplitude |
| `display.py` | 5 | ~370 | **get_display_hardware 151 + get_mouse_hardware 136 是最大的两个** |
| `presets.py` | 5 | ~100 | list/load/save/delete/import/export |
| `brand.py` | 5 | ~15 | background CRUD + themes |
| `ota.py` | 4 | ~110 | update_check/status/install + ota_install |
| `hooks.py` | 3 | 34 | `_enforce_gate` / `_handle_core_unavailable` / `_handle_payload_too_large` |
| `state.py` | 3 | 10 | get_state / get_events / get_config_web |
| `aim_trace.py` | 2 | 60 | start/stop aim trace + usb diag download |
| `pages.py` | 2 | 10 | desktop / mobile / index / activation_page |

**最大的两个函数单独处理**：`get_display_hardware` 151 行、`get_mouse_hardware` 136 行
—— 这两个是"读硬件 + 校验 + 拼装"三件事混在一起，拆成 `lib/hardware_probe.py`（读）
+ `lib/hardware_validate.py`（校验）+ 路由层（拼装）。**这一步会有真正的逻辑改动，
需要单独走一轮测试**，不能和 S9 混在一起。

### 2.2 依赖注入：hub.call → Deps 对象 ★关键

这是「可插拔」的真正前置条件。

**现状**（`state_snapshot.py` 有 17 处）：
```python
def _get_status(*args, **kwargs):
    return hub.call('_get_status', *args, **kwargs)
```

**改成**：
```python
class SnapshotDeps:
    """collect_web_state 所需的外部依赖。显式注入 ⇒ 可脱离 Flask 独立跑。"""
    def __init__(self, get_status, license_block, ui_block, ipc_request, ...):
        self.get_status = get_status
        ...

def collect_web_state(deps: SnapshotDeps) -> dict:
    lic = deps.license_block()      # 不再 hub.call
```

**入口装配**：
```python
def build_deps() -> SnapshotDeps:
    return SnapshotDeps(get_status=_get_status, license_block=_license_block, ...)
```

**为什么不一次性全改**：`hub.call` 是 S3/S4 定下的机制，正是它让 482 个测试
（其中 130 处 monkeypatch）保持绿色。一次全改会同时动37 个调用点 + 需要重写大量测试替身。
**分两步**：
- S9-a：只拆路由，hub 机制不动 → 验证「拆路由」这件事本身是安全的
- S9-b：逐模块把 hub 回调收成Deps，每个模块搬完跑一次全量

### 2.3 兼容层（不能省）

S9 之后入口只剩 250 行，但**测试仍会 `import` 入口并monkeypatch 那 130 个名字**。
所以入口必须保留一个 re-export 层：

```python
# 补丁锚点兼容层 —— 这些名字被 130 处 monkeypatch 依赖，不能消失
from plugins.web.api.state import get_state
from plugins.web.lib.state_snapshot import collect_web_state, _models_view
# ... 共 27 个名字
```

**这一层是硬约束**。删了它482 个测试直接红。

### 3.3 三条硬约束

1. **禁 `type="module"`** —— 内联 `onclick="foo()"` 依赖全局作用域，改成 ESM 会让所有
   内联事件处理器静默失效。必须用普通 `<script src>` 顺序加载。
2. **禁构建工具**（webpack/vite/esbuild）—— 引入 node_modules 就破坏"零依赖、离线、
   一份源码直接出包"的现有交付链。拆分必须是纯文本文件 + `<link>`/`<script>` 引用。
3. **12 个写死的 `/api` 路径一字不改** —— 前端不做任何 URL 重构。

### 3.4 前端测试的麻烦

**25 个测试文件里 17 个读源码文本**。拆面板会让这 17 个里的面板相关断言全部打红。
做法与 S5/S6 相同：断言改成「拼接多个源文件后检查」，并在测试里写明"以后再怎么拆都成立"。

**建议**：先做后端 S9，前端单独立项（P1）。理由 —— 后端拆完入口 250 行，
前端拆完模板 900 行，两者都到位才算结构清晰。混在一起做一旦打红无法定位是哪边引起的。

## 4. 执行顺序与风险

| 阶段 | 内容 | 验证门禁 |风险 |
| --- | --- | --- | --- |
| **S7** | 搬usbproxy 配置 + 硬件 payload（约 400 行） | 482 passed | 低。纯机械搬 |
| **S8** | 搬模型导入/转换 + activation/gate（约 400 行） | 482 passed | 低 |
| **S9-a** | 路由拆 14 个 Blueprint，入口降到 ~600 行 | 482 passed + **URL 逐字比对** | 中。URL 必须一字不改 |
| **S9-b** | hub 回调逐模块收成 Deps | 482 passed（每模块一次） | 中。测试替身要跟着改 |
| **S9-c** | 硬件两函数拆 probe/validate | 482 passed | **高。有真逻辑改动**，单独走 |
| **S10** | 入口降到 < 250 行，加 app 工厂 | 482 passed | 低 |
| **P1** | 面板拆分（CSS 5 + JS 12 + 模板 4） | 482 passed + **17 个读源码测试全改** | 高。前端无自动化测试兜底 |

### 关键风险

**R1· G3 零余量**（已在上一轮报告中记录）：现在正好 45 = 基线 45，
任何含 `/opt/ttbox` 等字面量的注释/字符串会让门禁 FAIL，且不能改基线表。
S7–S10 每搬一块都要盯。

**R2 · URL 漂移**：S9-a 拆 89 个路由时，任何一个 url_prefix 写错就是线上 404，
而 482 个测试**不一定覆盖全部 89 条**。

⇒ **已落安全网**：`scripts/web_route_snapshot.txt`（89 条 `METHOD URL 视图函数名`）。
S9-a 拆之前跑一次导入快照、拆之后跑一次比对，**逐条不同即 FAIL**。
比对脚本下一步就写（`scripts/check_route_snapshot.py`，届时与门禁 G8 挂钩）。

**R3 · 前端无测试兜底**：面板 7219 行 JS 拆开后，只有 17 个读源码测试保护，
没有真正的功能测试。⇒ 拆面板前必须先给关键交互补 Playwright 冒烟测试（可放 P0.5）。

**R4 · 482 个测试里有 130 处 monkeypatch**：任何拆域时漏了re-export 就红。
⇒ 兼容层名字清单要机械枚举，不能凭记忆。

## 5. 可插拔能力（做完之后能达到什么）

| 能力 | 现状 | S10 之后 |
| --- | --- | --- |
| 加一个功能 | 改 3645 行入口 | 新增 `api/xxx.py` + `register` 一行 |
| 摘一个功能 | 注释路由 | 从 `ENABLED_DOMAINS` 列表移除 |
| 按客户开功能 | 做不到 | `create_app(enabled=['aim','models',...])` |
| 单独测一个域 | 要起整个 Flask app | `register_blueprints(make_app())`，无需起服务 |
| 换存储后端 | 改 lib 内部 | 实现 Deps 协议，换注入对象 |

**这是渐进可逆的**：每一步都能独立验证，不满意就停在当步。
