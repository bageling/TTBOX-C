# TTBOX core（C++）优化方案

> 编制：2026-10-03 · 依据：本机静态度量 + **板端真实运行数据**（192.168.0.120，RK3588）
> 原则：先量后判，不做无证据的改动；结构清晰优先于局部提速

---

## 一、先说结论：core 的瓶颈**不在性能**

板端 V1.0.19 实测（跑起来 33 分钟）：

| 指标 | 实测值 | 判断 |
| --- | --- | --- |
| core 进程 CPU | **23.3%**（8 核 A55 @1.8GHz） | 宽松 |
| 内存 RSS | **174 MB** | 宽松 |
| 单线程最高 | 10.5%（瞄准线程） | 无异常忙等 |
| 日志报错/告警 | 30 分钟内 **3 条** | 健康 |
| 预览帧率 | 正常（未掉帧） | — |

**含义**：把 core 当"性能优化对象"是错的方向。真正该动的是**可维护性与防复发**——
core 有 30336 行 / 171 文件，任何一次改动都要靠 19426 行测试兜底，
而测试覆盖有**结构性缺口**（下表）。

---

## 二、四个真实问题（按风险排序）

### P0 · `AimThread::loop()` 单函数 893 行 —— 占 core 全域 3%

**实测**：L74 到文件末（967 行）= **893 行**，是 core 里最长的函数。
它是**瞄准控制链的主循环**，对延迟敏感、固定绑大核运行。

风险不是"慢"，而是**任何改动都要在 893 行里定位**，且这段正是产品核心手感。

拆分判据（不是按行数硬切，是按循环内的阶段）：

```
loop() 现状（893 行）应拆成：
  ├ 取帧（从邮箱取最新一帧，含去重）
  ├ 前处理（坐标系转换 + 目标选择）
  ├ PID 计算（比例/积分/微分 + 限幅）
  ├ 拟人化与抖动注入
  └ 输出（换算成设备计数 + 注入）
```

**验收**：拆分前后**同一段录像**的落点像素差 = 0。
（这是唯一有意义的验收标准——PID 有积分状态，行为等价必须逐位比。）

### P1 · 测试覆盖有缺口：4 个核心文件无对应测试

| 实现 | 行数量级 | 有无专测 |
| --- | --- | --- |
| `TargetSelector`（选靶） | 701 行 | **无** |
| `RuntimeProfile`（运行配置解析） | 384+305 行 | **无** |
| `WorkerPool`（推理线程池） | 304 行主循环 | **无** |
| `CoreRuntime`（五步编排） | 549 行 | **无** |

`test_aim_thread` / `test_decode` / `test_ipc*` 覆盖了周边，但**上面 4 个是"编排 + 解析"类**，
出错时不会崩，会**静默用错值**（比如配置解析漏字段 ⇒ 参数悄悄变默认值）。

**这是最该补的**：不是为了让覆盖率好看，是这 4 个地方**错了不会报错**。

### P2 · 硬编码板级拓扑：还剩 3 处

今天已修 2 处（风扇 `hwmon8`、UDC `fc000000.usb`）。
剩余 3 处 `/dev/video0`（`Application.cpp:333/336/340` + `V4L2Capture.hpp:85`）。

**这一处不同**：视频设备**有配置项覆盖**（`capture_device`），是合理的默认值；
而 hwmon/UDC 当时**没有任何覆盖路径**才必须改。
⇒ **建议不改**，但补一条注释说明"这是默认值，可被配置覆盖"，避免后人又照 hwmon 的思路改它。

### P3 · 单帧热路径上的容器分配

`DecodeNMS`（解码 + NMS）与 `AimThread` 每帧构造 `std::vector<DetectionBox>`。
当前 CPU 只用 23%，**没有证据说明它是瓶颈**。

⇒ **列为观察项，不动**。若将来 CPU 真的到 60%+，先量再改（预留复用缓冲，不要现在盲改）。

---

## 三、建议的执行顺序

| 阶段 | 做什么 | 为什么这个顺序 | 风险 |
| --- | --- | --- | --- |
| **1** | 补 `TargetSelector` / `RuntimeProfile` 两个测试 | 独立、无行为改动、能立刻给"改 core"上一道保险 | 零 |
| **2** | 拆 `AimThread::loop()`，**用录像逐位比对验收** | 有了阶段的测试兜底才敢动核心手感 | 中 |
| **3** | 补 `WorkerPool` / `CoreRuntime` 测试 | 编排类同样"错了不崩" | 零 |
| **4** | 给 `/dev/video0` 补注释 | 防止后来人重复今天的无用功 | 零 |

**先 1 后 2** 的理由：先有测试网，再动最危险的那块。反过来做就是把 893 行核心逻辑
在没有安全网的情况下改——那正是今天 web 侧两次事故的同款剧本。

---

## 四、明确不建议做的

| 事项 | 为什么不做 |
| --- | --- |
| 按"性能优化"改 core | 板端 CPU 23%、内存 174MB，**没有可优化的性能瓶颈** |
| 为覆盖率而补测试 | 只补 4 个"错了不崩"的编排/解析类，不追数字 |
| 现在改单帧容器分配 | 无证据（CPU 23%），属于盲改 |
| 改 `/dev/video0` 为运行时解析 | 它有配置覆盖，不属于"写死"缺陷；照 hwmon 那套改是过度工程 |
| 拆 `Application::initialize`（492 行） | 它是启动装配，拆了会打散"五步顺序"这条硬约束的可读性 |
