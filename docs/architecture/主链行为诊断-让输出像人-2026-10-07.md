# 主链行为诊断 —— 让输出像人（2026-10-07 第 5 轮终版）

> 业主要求：「审链路问题，用外挂开发者的思维，符合人类逻辑」。
> 方法：主理人做 PID 数学形状实测 + 3 位队友并行（时序 / 参数耦合 / 实战失效），并**互相交叉纠错**。
> 本文是三轮交叉核对后的收敛结论。行号为当前工作区。

---

## 0. 主链与判据

```
V4L2Capture → RGA裁剪 → RKNN推理 → DecodeNMS解码 → TargetSelector选靶
→ AimPointProfile落点 → AimTracker平滑 → Pid1Controller PID → 输出HID
```

**「像不像人」的判据**（真人一次瞄准移动的时间序列）：
1. 起步爆发 2. 接近减速 3. **到位小幅过冲** 4. **回拉微调** 5. 全程微抖 6. 遇到偏差会「攒」修正量

---

## ★★★ 三条根因（都经实测/核实，不是推测）

### 根因 A：板端 PID 退化成「纯 P+D」，输出**永不过冲** ⇒ 不像人

**实测**（`pid_human_probe.cpp`，板端参数 kp=25 kd=25 smooth=9900 gain=0.65 predict=0）：
```
帧0 误差300 → 一步52.8px（爆发 ✓）
帧1~23 平滑递减 21.8→1.9px（减速 ✓）
符号翻转 = 0 次 ⇒ 永不过冲 ✗
```
对照 `predict=1`：翻转 2 次、有轻微过冲 ⇒ **预测项才是"像人"的来源**。

**机制**：`Pid1Controller.hpp:112` `ki_raw = ki_raw * predict * integral_gain`。
板端 `predict_x=0, predict_y=0` ⇒ **`K_i ≡ 0`，两轴只剩 P+D**。
而 P+D 的输出 ∝ 当前误差 ⇒ 大偏差时最猛、小偏差时最弱 ⇒ **不会"攒"修正量**（违背判据 6）。

★ 硬证据（主理人实测）：误差 300px 时一步 81 count，误差 14px 时一步 3 count。
**大偏差 / 小偏差的输出差 27 倍** ⇒ 系统天生"冲过头猛拉、接近时不敢动"。

### 根因 B：`smooth=9900` 把 P/D 压到 **1%**，而 `K_i` 不受它管 ⇒ **前馈 : 反馈 = 90 : 1**

`Pid1Controller.hpp:121-123`：
```cpp
K_p = smoothTerm(K_p, bw, bw - smooth);       // smooth=9900 ⇒ outputScale = 100
K_i = smoothTerm(K_i, bw, bw - 1000.0);       // ★ 恒 9000，完全不受 smooth 影响
K_d = smoothTerm(K_d, bw, bw - smooth);       // 100
```
★ **这就是 `MouseTypes.hpp:432` 注释说「前馈主导」的结构根因。**
★ **业主没有任何旋钮能调 Ki 音量**（`predict` 是输入开关，不是音量）。

**实测放大**（主理人跑 `smoothTerm`）：
| 误差 | Kp原始 | 经 smoothTerm | 实际放大 |
|---|---|---|---|
| 10px | 250 | 2.50 | **0.0100** |
| 100px | 2500 | 22.59 | **0.0090** |
| 300px | 7500 | 40.59 | **0.0054** |

⇒ **面板上 kp=25，实际有效比例增益约 0.25。**

### 根因 C：★「越打越慢」—— PID 输出无界，累积控制量 ∝ 误差

`Pid1Controller.hpp` **没有任何输出饱和限幅**。`K_i` 随误差增长 ⇒ 累积控制量 ∝ 误差
⇒ **偏得越多，收回来越慢** ⇒ 业主描述的「**越打越慢**」。

★ **两条独立路径指向同一结论**：
- 静态分析（chain-practice）：`Ki ∝ 稳态误差`，输出无界
- 数学实测（主理人）：`Ki` 稳态趋近 `1−|err|/50` ⇒ **误差越大、这一帧挪得越少**

⇒ **这是「跟手度不足」的物理主因，比调 kp 更本质。**

## ★★ 一条救命通道（解释业主体感）

`Pid1Controller.hpp:115-117`：`K_p` / `K_d` **完全不经过 predict**。
⇒ 即使 predict 配错 100 倍，**仍有比例项兜底**，系统只会"变黏/变慢/抖"，**不会完全失灵**。
★ 这解释了业主「参数配错了但没完全失控」的体感。

## ★★★ 三个真 bug（改动极小、收益大）

### B-1 `trim_tracks` 排序方向反了（**删最健康的、留最陈旧的**）
`TargetSelector.cpp:286-295`：comparator 把「丢失多 / 更早未见」排**前**，`pop_back()` 删**尾**
⇒ 优先删「刚丢的新鲜轨迹」，僵尸全留。
★ 业主症状：**切目标后短暂失灵**、多目标**跳着打**。
★ **修法**：`pop_back()` → `erase(begin())`。

### B-2 `lost_frames` 冻结 ⇒ 第一个删除条件**永不成立**
三处 `lost_frames++`（`TargetSelector.cpp:235/380/522`）全在 `if (t.active)` 内
⇒ 非激活轨迹计数永久冻结 ⇒ `!active && lost_frames > buffer` 永假
⇒ 全靠 `max_tracks` 那条 pop_back 兜底 ⇒ **与 B-1 叠加：先删新鲜的、僵尸全留**。

### B-3 `pull_curve` 出厂默认开 + `out_x==0` 注入 +24 纯 Y 偏移
`PullCurve.hpp:34`：`const float dir = (out_x >= 0.0f) ? 1.0f : -1.0f;`
**X 恰好不动的那一帧也被判为 +1** ⇒ 注入 **+24 count 纯 Y 偏移**。
出厂 `pull_curve.enabled=true, min_distance=80`（面板不提示它会注入垂直偏移）。
★ 业主症状：**「打完向右上角拉一下」「准星莫名向上一跳」**。
★ **修法**：加 `if (std::fabs(out_x) < 1.0f) return 0.0f;`

## ★★★ 一条需业主拍板的面板问题

**面板在教业主错误的操作模型。**

`index.html:265` 写「V1.0.43 起默认用 **Fitts 控制器**…老 pid 保留为备选」，
但 **Fitts 昨天已被业主下令删除**（git `6a868c9`，16 文件全清）。
- 那个"控制器下拉框"HTML **是破损的**：`<option>` 无 `<select>` 开标签、闭标签孤立 ⇒ 浏览器**丢弃整块**。
- 下方「Fitts 控制器（当前默认）」的输入框区**是空的**。
- `MouseTypes.hpp:435` 注释仍写「默认 fitts；pid1 保留备选」——**与代码相反**。

⇒ 面板说「切到老 pid 那五个参数才生效；Fitts 模式下它们被忽略」——
**core 里只有 pid1，那五个参数永远生效**。业主为"避开 Fitts"而特意调那五个数 = 白调。

**建议**：**删文案**（纯 HTML/JS，零行为风险）vs 重做 Fitts（改闭环需重标定）。

## ★ 参数「名字骗人」清单

| 参数 | 面板标签 | 实际作用 | 调错的后果 |
|---|---|---|---|
| `smooth` | 「缓冲」 | **削弱倍率** `10000−smooth`，越大输出越弱 | 调"更稳"反而输出砍到 1/10 |
| `predict` | 「预判」 | **输出自激励前馈**（`last_u*gain`） | 当"预测"调会发散 |
| `rate` | 「跟随速度」 | `kp_gain` 的爬升速率 | 调大 = 更凶 |
| `output_deadzone` | 「小于它就不动」 | **余数累积**，决定"多久发一次" | 余数一直保留，没被丢 |
| `mouse.fov_range` | — | **零消费死字段**（真正生效的是 `fov.radius`） | 改了没反应 |
| `deadzone_x/y`、`OutputScale`、`RateLimiter` | — | **生产零 include**（仅测试用） | 看着像兜底，其实没有 |

### ★★ 两条最危险
1. **`smooth=0` ⇒ 整个软限幅块被跳过 ⇒ 输出暴涨 100 倍**（`Pid1Controller.hpp:120` 的 `if (smooth)`）。
   面板滑杆范围 `[0,9999]`，**0 就在最左边**，而 `RuntimeProfile` 只校验上界。
   ⇒ `MouseTypes.hpp:425` 自述「之前恒传 0.0 等于把最重要的一道大误差保护整个关掉」——
   **V1.0.13~V1.0.37 业主一直是在这层保护全关的状态下调参的**。
2. **`predict` 无任何上限校验**（`RuntimeProfile.cpp:172-189` 只校 kd/kp/smooth/rate），
   而面板允许填到 **10** ⇒ 回路上溢发散。
   稳态边界：`predict × gain × ig ≈ 1`，ig 随误差在 0.60~0.98 ⇒ **predict ∈ [1.53, 2.50] 就发散**。

## ★ 修正声明（两位队友交叉纠错，最终采纳）

- **作废**：「跑到头上 = capture=0 fallback 失效」——板端实际跑 `capture=416`
  （`AimThread.cpp:203-206` 与 `AimPointProfile.cpp:45-49` 同一组实测注释），fallback 路径是走的。
- ★ **修正后的真实根因**：`offset_y` 默认值问题。主理人核实：**三个默认值并存且互相矛盾**——
  `MouseTypes.hpp:68`（ClassOffset）`0.5`、`:96`（AimPointProfile）`0.5`、`:139`（AimHotkeyProfile 档位表）`0.5`；
  而代码注释的实战口径是 **0.31**（`AimPointProfile.cpp:49`）和 **0.24**（`:134`）。
  ⇒ 冻结机制（`FrozenRect.hpp:9-11`）本身在正常工作，但默认 0.5 让它的抵消效果打折扣。
- **限定**：「回退 720px」只是 2560×1440 的特例（1080p⇒540px、720p⇒360px）。
- **撤回**：`crop_bottom_px_` 陈旧值风险（`AimThread.cpp:215` 的 else 分支有兜底，结构是对的）。
