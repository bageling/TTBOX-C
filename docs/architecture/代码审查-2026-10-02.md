## 6 项发现

### 1· 死代码：**零个**（此处差点误判，已推翻）

第一版 AST 检测报出 25 个「死代码」，逐个 grep 实证后**全部推翻**：

| 报为死代码                   | 实际情况                                                |
| ----------------------- | --------------------------------------------------- |
| 89 个路由函数                | 装饰器即入口，天然「无人调用」                                     |
| `paths.py` 的 13 个函数     | 通过 `ttbox_paths.models_root()` 属性访问，我的 Load 计数漏了属性链 |
| `hub.bind` / `hub.call` | 入口用 `hub.bind(...)` 属性调用                            |
| `add_no_cache_headers`  | ★ **`@app.after_request` 钩子，实测响应头确认生效**             |

**最后一个最险**：它有 `@app.after_request` 装饰器，AST 里看不到任何调用点，  
grep 也只找到定义行 —— 三条判据全过。若直接删，**全站缓存策略当场失效**。

实测证据：

```
app.after_request_funcs[None] = [add_no_cache_headers L580]
GET /api/state → Cache-Control: no-store, no-cache, must-revalidate
                 Pragma: no-cache
```

⇒ **结论：`lib/` + `api/` + 入口，无死代码。**

★ **教训（比结论更重要）**：「AST 零引用 + grep 只剩定义行」**不足以判死代码**。  
必须再问一句：**这个名字是不是被框架按名字调用？** 本项目的框架钩子有  
`@app.after_request` / `@app.before_request` / `@app.errorhandler`，  
加上 Jinja 模板宏、`__all__` 导出、桌面/移动分流的元数据 —— 这些都不产生调用点。  
**动手删之前，先把被删的东西从框架里摘出来实测一次。**

### 2 · `state_snapshot.py` 依赖 17 个入口名字（耦合最重）

它把 8 个 payload 聚合起来喂给 `/api/state`（`_core_state_payload` / `_calibration_payload`  
/ `_auto_start_payload` / `_fan_control_payload` / `_loopout_payload` / `_cloud_license_subblock`…）。

**这是设计使然，不是缺陷** —— 聚合器本来就要收集多个源。但它是整个 lib 层里  
反向依赖最重的一个文件，**要盯住别继续加**（S9-b 收 Deps 注入时优先处理它）。

### 3 · 4 个 lib 文件超 300 行

已全部登记，门禁 G1 盯住「不跨 100 行位」的硬上限。  
`calibration.py` 794 行是标定算法本体，内聚且有大量注释，**不建议为拆而拆**。

### 4 · 裸 `except` 101 处 —— ★ 门禁口径盲区

| 文件               | 处数 |
| ---------------- | -- |
| calibration.py   | 15 |
| motion.py        | 13 |
| sysinfo.py       | 11 |
| model_convert.py | 7  |
| 其余 15 个模块        | 55 |

**门禁 G2py 的基线 72 是在 `core/src core/include plugins framework ttbox_platform
ttbox_motion` 等目录统计的，`lib/` 不在其中** ⇒ 这 101 处门禁完全看不见。

⚠ **这是审查发现的最值得注意的结构性事实**：`lib/` 处于门禁的**盲区**。  
现在数量可控（101 处，形态与原入口一致），但**没有任何机制阻止它增长**。

⇒ 建议：把 `plugins/web/lib` 与 `plugins/web/api` 纳入 G2py 统计范围，  
当前值作为新基线登记（棘轮只许减不增）。**不需要现在做**，但应该有这条约定。

### 5 · 域之间零import，边界干净（✓ 通过）

`api/` 各域**互不 import**，只走 `lib` 与 `hub`。这是拆 Blueprint 时定下的约定，  
实测成立。12 个域全部拆完后，`api/` 会反向引用 `lib` 的 20+ 个名字，  
**那时耦合面才真正定型** —— 建议拆完再做一次本审查。

### 6 · `index.html` 13446 行 —— 唯一真正高风险的动作

- CSS 5188 + HTML 1030 + JS 7219，396 个顶层 JS 符号。
- 17 个测试读它源码（约束 B）。
- **没有功能测试兜底** —— 拆开后只有「读源码文本断言」保护，    
  这类断言只能证明「某段代码还在」，证明不了「交互还对」。

⇒ 拆之前**必须先补关键交互的 Playwright 冒烟测试**。这是全部审查结论里  
唯一一条「不满足前提就别动手」。
