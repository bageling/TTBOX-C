#项理由

4.6 修复顺序与验收（分步 + gate + 回滚）

关键设计：唯一一次上板同时产出「基线数据 + 修复验证 + 新增 aim 仪表数据」。
  • Step 0 · 冻结基线（同一上板 session 前半段）：先读面板 decode_ms / decode_p50/95/99、e2e_p50/95/99、infer_ms、fps、CPU%、RSS 并归档。Gate0：数据成功读取并归档——若读不到，不得烧修复批次。
  • Step 1 · 必改批次（A1–A4 + 随批 B1–B7）：编译 → 单测 → 离线回放/soak → 板端验证。Gate1：① 零新增告警；② 单测全过；③ 离线回放/soak 无回归；④ 板端开 pid_trace 正常落盘；⑤ 面板 last_dequeued_count 稳定、aim_ms/p50/p95 非 0。
  • Step 2 · 读数据判性能（纯读，不烧板）：读 aim_ms/p50/p95 + decode_ms/p95 + e2e_p95/p99。Gate2：只有到这一步、且尾延迟显示实际瓶颈，才允许讨论 C1 性能重构；否则关闭性能议题。
  • Step 3 · 有条件重构（仅当 Gate2 触发）：先补离线回放测试再动结构。Gate3：结构化改动必须有回放对照（逐位/统计等价）。

回滚总纲：A/B 类全部单文件、无跨文件签名变更 ⇒ git revert <commit>。这正是裁决人否决"改 start() 签名"版的根本原因。

5 · 遗留待业主决策（必须拍板）

  1. HARDWARE_ACTION 脚本超时（IpcServer.cpp:752）：脚本/systemctl 潜在无界 ⇒ 脚本挂住则 Application::shutdown() 永久退不出（关机/重启会卡死）。选项：(a) 硬化——shared_ptr+enable_shared_from_this（需把 Application.hpp:164 按值 IpcServer ipc_; 改 shared_ptr）+ handler 超时；(b) 运维约束——要求脚本自带限时。涉及关机安全性，需业主选。
  2. web 是否独立发布：决定 C4（web/core 分离、单一静态库拆分）的优先级。若不独立发布，C4 可长期不动。
  3. decode_ms 端到端现状核实：代码已证有产出，但板端面板显示值需在 Step0 确认非 0；若为 0 ⇒ 上游统计吸收点断线，需单独排查。
  4. 一次上板窗口安排：必须同一 session 内先采基线、后烧修复批次，否则拿不到修复前基线。
  5. B1 落盘路径/权限：aim 阶段 trace/计时在板端的落盘位置与 root 权限确认。
