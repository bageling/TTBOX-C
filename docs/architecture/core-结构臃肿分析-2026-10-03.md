# TTBOX core 代码臃肿与结构分析

> 编制：2026-10-03 · 依据：core/src 171 文件全量静态度量（不含估计值）
> 结论一句话：**core 不胖，但有 4 处"结构性的乱"**——注释不虚胖，
> 真问题是「一个文件塞了多件事」+「两个空目录」+「实现散落在别处」+「巨型函数」。

## 二、四个真实问题（按"结构混乱度"排序，不是按行数）

### S1 · `Application.cpp` 一个文件塞了 5 类职责（2334 行 / 36 个成员函数）

实测分类：

| 职责 | 函数数 | 代表 |
| --- | --- | --- |
| 杂项工具 | **15** | `build_runtime_params` / `apply_preview_degrade` / `migrate_output_enabled` / `current_feature_gates` |
| **IPC 命令处理** | **11** | `handle_runtime_control` / `handle_config_update` / `handle_model_import` |
| 授权 | 5 | `license_status_snapshot` / `license_allow_run` |
| 生命周期编排 | 4 | `initialize` / `run` / `shutdown` |
| 品牌主题 | 1 | `brand_upper` |

**问题**：11 个 IPC 命令处理器和 15 个工具函数混在同一个类里。
改一条 IPC 命令要在一个 2334 行文件里定位；工具函数的改动会碰到 IPC 注册表。

**改法（不拆类，拆文件）**：
```
app/Application.cpp        保留：生命周期编排（initialize/run/shutdown）+ 装配
app/ipc_handlers.cpp       移入：11 个 handle_*（IPC 命令处理）
app/runtime_params.cpp     移入：15 个工具（功能门/预览降级/参数构建）
```
外部行为零变化（成员函数还是同一个类的，只是定义移到别的编译单元）。

### S2 · 两个空目录（`controller/` `coordinate/`）

实测：**目录里一个文件都没有**，全仓 `grep` 无任何引用（连注释里的"旧 controller/PidController"都是历史）。
⇒ 纯残留，**直接删**（删目录不删代码，零风险）。

### S3 · `pipeline/` 与 `detector/` 是 header-only 域：4 个头、0 个实现文件

| 域 | 头文件 | .cpp | 性质 |
| --- | --- | --- | --- |
| `pipeline/` | 3 个 | **0 个** | `AimTargetMailbox`（6 个方法）+ `AimTargetTask` + `Target` |
| `detector/` | 1 个 | **0 个** | `IDetector`（纯接口） |

**这是合理的**（小而热的值对象，inline 在头里避免调用开销）。

**但代价是**：这两个域**在目录结构上完全看不出实现**——按 `pipeline/` 找实现会扑空，
只能翻头文件才知道代码写在 `inline` 里。
⇒ 建议：**不改结构**，只在两个域各加一行头注释说明"本域为 header-only，实现 inline 在头文件中"，
让"找不到 .cpp"这件事变成**有意设计**而不是**疑似缺失**。

> ⚠️ 本文初稿曾把这条写成"实现散落在 `runtime/CoreRuntime.cpp`"，
> **复核时证伪**：`AimTargetMailbox::` 在 CoreRuntime 里出现的只是
> `kMaxWorkers` 常量引用，不是函数实现。

### S4 · `AimThread::loop()` 单函数 893 行（占 core 全域 3%）

实测：L74 → 文件末（967 行）。瞄准控制链主循环，**对延迟敏感、绑大核运行**。

**风险不是"慢"（CPU 只 23%），是"任何改动都要在 893 行里定位"**，而这正是产品核心手感。

**改法**：按循环内的阶段拆 5 段（取帧 / 前处理 / PID / 拟人化 / 输出）。
**验收标准只有一个：同一段录制输入，拆分前后落点像素差 = 0**（PID 有积分态，必须逐位比，不是"差不多"）。

## 三、附带发现（不是问题，但值得记）

- **`/dev/video0` 写死 3 处**（`Application.cpp:333/336/340`、`V4L2Capture.hpp:85`）——
  **建议不改**：它有 `capture_device` 配置项覆盖，是合理默认值。
  与已修的风扇 hwmon/UDC 不同（那两个当时**没有任何覆盖路径**）。
  补一行注释即可，避免后来人又照 hwmon 的思路来"修"它。
- **同名函数 61 个**——查过是误报：`configure`/`close`/`destroy`/`detect` 是不同类型的
  各自方法，本来就该重名。**不是重复代码。**

## 四、建议执行顺序

| 阶段 | 做什么 | 风险 | 为什么这个顺序 |
| --- | --- | --- | --- |
| 1 | 删两个空目录 + 补 `/dev/video0` 与 header-only 两处注释 | **零** | 纯清理，先把地基弄干净 |
| 2 | 补 `TargetSelector` / `RuntimeProfile` 测试 | 零 | 给后面拆函数上一道保险网 |
| 3 | 拆 `Application.cpp`（按职责分 3 个编译单元） | 中 | 只搬定义，成员函数不动 |
| 4 | 拆 `AimThread::loop()` + **录像逐位比对验收** | **中** | 最核心的手感，放最后做 |

**顺序的逻辑**：零风险的先做（1）→ 建安全网（2）→ 只搬定义（3）→ 动核心手感（4）。
反过来做就是在没安全网的情况下改最危险的部分。

> 初稿里的「第 3 步：`pipeline/AimTargetMailbox.cpp` 搬家」经复核**取消**——
> 该域本就是 header-only，无处可搬（见 S3 修正）。

## 五、本文的复核记录（2026-10-03 二次验证）

| 结论 | 复核方式 | 结果 |
| --- | --- | --- |
| 体量构成（74% 真代码） | 重复跑 3 次 + **换 shell 工具链**（`wc`/`grep -c` 独立复核） | **一致**。`wc` 报 30336 而逻辑行 30338，差 2 行已定位：`AimStateMachine.cpp` 与 `LocalHidBackend.cpp` **缺末尾换行**，`wc` 因此少算 2 行 |
| ≥80 行函数 = 28 个 | **两种独立方法**（花括号深度 / 闭括号行）交叉验证 | **28 vs 28，逐个行数相同，零分歧** |
| 两个空目录 | `find -empty` 跑 3 次 + `ls -A`（含隐藏）+ `git ls-files` | **确认为空且 git 未跟踪** |
| Application 成员 = **36** 个 | 两种口径（列 0 的定义行 / 匹配 `Application::`） | **均为 36**。`grep -c "Application::"` 得 40 是因为**其中 4 处是注释里的引用**；`^[A-Za-z_].*::` 得 49 是因为**另有 13 个是命名空间级函数**（`shutdown_flag` / `env_or_empty` / `parse_log_level` 等），不属于 Application 成员 |
| pipeline/detector 性质 | 查头文件 inline 定义 | **初稿判断错误，已修正为 header-only** |

## 六、明确不建议

| 事项 | 原因 |
| --- | --- |
| 为"文件太大"而拆 `IpcServer.cpp`（1240 行） | 它是**单一职责**（IPC 传输 + 命令分发），不臃肿；按行数拆会打断协议解析的连续性 |
| 把 `AppConfig`/`RuntimeProfile` 合并 | 已实测是 5 层单向依赖，**分层清楚**，不需要"优化" |
| 追注释覆盖率 / 加 Code Metrics 门禁 | 本仓注释密度已正常，指标不是目的 |
| 改 `/dev/video0` 为运行时解析 | 有配置覆盖，属过度工程 |
| 拆 `Application::initialize`（492 行） | 它就是启动装配，**五步顺序的可读性**就是它的价值；拆散反而更难读 |
