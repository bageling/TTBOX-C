## 0. 一句话总览

TTBOX 是一个**纯视觉 AI 自瞄盒子**（RK3588 arm64）。信号链：

```
HDMI 采集卡 → V4L2 采集(640×640 居中裁剪) → RGA 硬件加速预处理 → RKNN NPU 推理
   → 检测解码 + classwise NMS → 目标选择(track_lock→rect_lock→score 三层)
   → 落点计算(框内比例) → PID 控制器 → 压枪/扳机/拟人化整形
   → 死区 → remainder 亚像素结转 → int16 量化 → HID 报告
   → USB gadget 注入 PC 鼠标
```

★ **根本认知（2026-10-07 确立，写在这里以免后人重犯）**：  
纯视觉方案拿不到视角角度与 FOV，因此**全链路是像素域闭环，没有角度域换算**。  
已核查业主提供的 7 个项目 + BB-828(5386 行)/yey(2498 行)源码：  
除读内存的 DMA 类外，全部纯视觉方案都是像素域闭环；`fov` 在 BB-828/yey 全文命中 **0** 处。  
`fov_mode` 半成品已删（commit `bc0ea35`）。移动预测靠 `predict` 前馈 + 标定 gain，不用 atan。

## 2. 采集链路（`core/src/capture/`, `core/src/rga/`, `core/src/edid/`）

### 2.1 V4L2 采集（`V4L2Capture.cpp` 822 行 + `DmaBuf.hpp/cpp`）

**打开流程**（每步都有错误回传，不静默失败）：

1. `open("/dev/video0")` → `VIDIOC_QUERYCAP` 校验 `V4L2_CAP_VIDEO_CAPTURE_MPLANE` + `V4L2_CAP_STREAMING`
2. `VIDIOC_G_FMT` 读当前格式（MP = **MPLANE 多平面**，非单平面）
3. **★ hdmirx 格式稳定等待（三段判据，实测优化）**
4. `VIDIOC_G_FMT` **重读比对** —— 格式真变了则整体重试（最多 5 轮）
5. `VIDIOC_S_SELECTION` → `V4L2_SEL_TGT_CROP` 设裁剪区
6. `VIDIOC_REQBUFS`（MMAP，默认 8 个 buffer，驱动实际为准）
7. 每 buffer 每 plane：`QUERYBUF` + `mmap` + **`VIDIOC_EXPBUF` 导出 DMA-BUF fd**（失败仅该 plane 无 fd，不整体失败）
8. `QBUF` 入队 → `STREAMON` → `DQBUF` 取流

**★ 像素格式映射**（`map_pixel_format`）：  
`BGR3 → kBGR888`｜`RGB3 → kRGB888`｜`RGB32/BGR32 → kRGBA8888`｜`NV12 → kNV12`  
（板端实测读到的是 **2560×1440 BGR3**）

**★ 800ms 等待优化（启动耗时治理，有实测证据）**：  
原逻辑「无条件 sleep 800ms → 重读 G_FMT 比对」。实测（板端 192.168.0.120，uptime 4.6 天）  
连续 40 次全新 open 读到的格式**全部是 2560/1440 BGR3，一次都没变** ⇒ 驱动早已过渡完毕，这 800ms 纯属白等。  
冷路径 start = **1.07s**，热路径 = **0.25s**，差的正是这 800ms。

新判据（按序，命中即跳过）：

1. **热重开**：距上次 close < `kWarmReopenWindowMs`(5s)（设备节点一直没断电，只关了自己的 fd）
2. **已启动** ≥ `kBootSettleSec`(60s)（读 `/proc/uptime`；hdmirx 格式 change 只发生在开机后 1~2 秒）
3. **兜底**：照旧睡满 800ms（开机不到 60s、或 uptime 读不到）⇒ 行为与修复前**逐字节一致**

跳过等待后**仍会做 G_FMT 重读比对**，一旦格式真变了仍走原重试逻辑 —— 只是不再「主动等」。

**其他**：

- 资源 RAII：`BufferRes`（mmap + dma-buf fd 自动释放）、`captured` 标记位图
- **跨线程"已 DQBUF 未归还"计数用原子计数器**（采集线程 fetch_add/sub，IPC/status 线程只 load）
- 打开失败时的清理：只有全部成功才置 `opened_=true` ⇒ 中途失败（QUERYBUF/mmap/EXPBUF/REQBUFS）会早退 close，不泄漏 fd
- `capture_cpu_affinity` + `capture_buffers` 可配
- ⚠ **已知缺陷**：`V4L2Capture.cpp:285` 附近区域的**硬件裁剪 ioctl 不生效**（审计 Q4，唯一核心链路 bug，走专项通道）

## 4. ★★ 算法核心（`core/src/mouse/` + `core/src/aim/`）— 本项目技术密度最高处

### 4.1 目标选择（`TargetSelector.cpp` 796 行 + `.hpp` 343 行）★ 最复杂

#### 4.1.1 内部结构：Track 表 + ByteTrack 卡尔曼

**`TrackEntry`（每目标一条）**：

- **ByteTrack 卡尔曼状态**：匀速模型 `[cx, cy, w, h, vx, vy, vw, vh]`（8 维），  
  关联时用**预测中心** `(pred_cx, pred_cy)` 作参考点
- `hits` / `confirmed`（hits 达标才确认）—— **ByteTrack 的 confirmed 语义**
- `created_ms` 用于**存在时长排序**（裁剪最旧）
- `last_seen_ms` / `lost_frames` / `active`

**`TargetSelection`（输出）除框与 id 外还带三个算法语义标记**（上游据此做不同处理）：

| 字段           | 含义                                                                                         | 上游动作                       |
| ------------ | ------------------------------------------------------------------------------------------ | -------------------------- |
| `Reason`     | `kNone`/`kTrackLock`/`kRectLock`/`kScore`（`enum class`，2026-10-07 整改；原为裸枚举会泄漏作用域且可隐式转 int） | 选靶层级可观测                    |
| `held`       | 本帧几何**没更新**，用的是上一帧的框（照 yu `*_holding_previous`）                                            | 遥测：这帧量测被判为坏                |
| `continuity` | 本帧是「同一目标的延续」而非新目标（id 变了但框重叠 + 尺寸一致）                                                        | **不重置平滑器/PID**（避免落点跳与重新起步） |

**★ 量测跳变门控（V1.0.11，照 yu `jump_rejected_holding_previous`）**：

- `d_hist[4]`：最近 4 次**被接受**的帧间位移（px）
- 用**中位数**当「局部速度」基准 —— 单帧噪声不会抬高基准（均值会被尖峰污染），  
  真运动则基准随之上抬、**阈值自动放宽**
- `hold_frames`：连续 holding_previous 帧数，到 `kMeasMaxHold`(10) 就**必须认输放行**（防锁死）
- `rejected_total`：累计拒绝帧数（遥测用，看门控有没有在工作）

**track 世代隔离**：`reset()` 后新世代 track id 从 1 重新开始，**禁止继承旧模型身份空间**。

#### 4.1.2 三层选择层级

1. `selector_track_lock` — 候选中存在与上帧相同 `track_id`
2. `selector_rect_lock` — track id 变但矩形匹配（同一目标被重编号），判据 `kContinuityIou=0.5` / `kContinuitySizeRatio=1.20` / `kContinuityMaxGapMs=300`
3. `selector_score` — 无锁定时按距离+尺寸综合评分

**关键常量**：

| 常量                       |    值 | 作用                 |
| ------------------------ | ---: | ------------------ |
| `kMeasJumpAbsPx`         |  8.0 | 量测突变绝对阈（px）        |
| `kMeasJumpRel`           |  3.0 | 量测突变相对阈（倍）         |
| `kMeasMaxHold`           |   10 | 保持上一帧量测的最大帧数       |
| `kSizeRatioCap`          | 1.35 | 框高比**硬上限**（配置只能更严） |
| `kSwitchConfirmRadiusPx` |   40 | 切靶确认窗半径            |
| `kLockLossWindowMs`      |  500 | 锁定丢失观察窗            |

**八大机制**：

1. **量测有效性门控**（yu 口径）：框突变/贴边/尺寸非法 → **拒绝量测 + 保持上一帧**，不修坏量测
2. **贴裁剪区边界剔除**：`reject_clip_horizontal`（默认开）+ `reject_clip_top`（默认关，近身仰角易误伤）。实测贴边帧只占 0.7% 却贡献全部位移尖峰（p90=27 vs 非贴边 p90=3）
3. **锁定尺寸一致性**：`track_size_ratio=1.35`，防 cls5↔cls0 两套人体框跳变（实测跨类别 |Δtgt_y| p90=64 vs 同类别 p90=10）
4. **丢失宽限**：`lost_grace_ms` 默认 78ms（对齐 BB 30ms 可调）
5. **自适应锁定半径**：`max(1.0, 0.06 × 框宽)`
6. **切靶防抖**：`switch_hysteresis=0.5`（新目标需近 50%，平方比省 sqrt）+ `switch_cooldown_ms=600`
7. **开火期禁切靶**（`fire_active`，照 yu `fire_switch_guarded`）：压枪时切靶=最难看的晃
8. **切靶确认窗**：`switch_confirm_frames=4`（照 yu `pending_switch_frames`），新目标需连续出现 4 帧

**★ V1.0.40 动态选靶范围**（移植 BB-828 :4576-4582，2026-10-07 最新提交）：  
框面积 = 距离的代理量。`area ≤ box_min_px2(200)` → 用 `min_px(40)` 小范围只锁准的；  
`area ≥ box_max_px2(1200)` → 全范围 `search_radius_px`；中间线性插值。**默认关**。

**其他几何机制**：

- `min_aspect_h_over_w=1.15` 高宽比下限（实测球 0.88 / 人 1.68~3.55，界取 1.15）
- `search_radius_px`：板端填 `min(capture.w,h)/2=320`（⚠ 默认 0 会让贴边剔除整条路径静默失效）

### 4.3 ★ PID 控制器（`aim/Pid1Controller.hpp` 237 行）— 唯一控制器

**算法来源**：外部 `pid1.cpp`（2026-08 用户提供），**只移植不改公式**。

```
输入 error(px)：
  |error| < 0.3            → error = 0
  |error - last_error| > 30 → reset()
  adjust_integral(error)  → integral_gain ∈ [0,1]，阈值 50.0，rate 0.025
  kp_integral(error)       → kp_gain      ∈ [0,1]，阈值 1920.0，rate 0.03
  error_diff = error - last_error
  target_velocity = error_diff + last_u × gain_     ← ★唯一改动行
  ├ 速度卡尔曼：q=0.01, r=1.0（一维 KF）
  ├ 近点分支(|err|<1 且 |diff|<0.1)：× gain_ × 0.5
  └ ki_raw = |ki|>0.5 ? ki : 0;  × predict × integral_gain → 积分卡尔曼 q=0.5,r=1.0
K_p = kp × error
K_i = ki_raw
K_d = kd × (error - last_error)
if (smooth): 三项各过 smoothTerm(soft-limit)
             K_i 的 outputScale 固定 bandwidth-1000
u = K_p + K_i + K_d
out = u × kp_gain
```

**soft-limit 公式**：

```
smoothTerm(v, bw, outScale) = (r×(1 + (4/15)r²) / (1 + (3/5)r²)) × outScale,  r = v/bw
```

**★ V1.0.39 唯一改动（单位换算）**：  
pid1 原文 `tv = error_diff + last_u` 隐含假设 **g=1（1 count = 1 px）**。  
板端实测 **g ≈ 0.65**（`mouse.gain_x_px_per_count`）。沿用 g=1 会**系统性低估目标速度 35%**  
⇒ 只能靠调低 predict 补偿（这正是 V1.0.13 把 predict 3.0→1.0 的真正原因）  
⇒ **换游戏灵敏度必须重调 predict**。接入 gain 后 predict 恢复作者原意。  
`gain_=1.0`（缺省）时公式**逐字节等于 pid1 原文**，`test_pid1` 对拍仍钉得住。

**★ V1.0.43 控制器选型**：pid1 实测「追着晃/停不住」（前馈主导对误差变化率敏感、  
P/D 被 smooth 压 100 倍 → 结构缺陷）。文档提到 Fitts 定律控制器  
`MT = A + B×log2(2|err|/W+1)`，仿真：不规则目标翻转 4（pid1 是 14，少 71%）、停得住。  
**但注意**：Fitts 控制器已按业主令删除（commit `6a868c9`「删除 Fitts 控制器，只留 pid1」）。

### 4.5 ★ 压枪（`RecoilController.hpp` 213 行）— 2026-09-30 按 yu 重做

**公式（纯 Y，X 恒 0，无枪械表）**：

```
每帧拉量(px) = 3 × strength × speed × ramp × dt
  strength ∈ [0,300]（默认 100）   speed ∈ [0.1,3.0]（默认 1.0）
ramp = 1                                     开火中（全量）
     = 1 - curve_strength × smoothstep(t/80ms)   释放后渐出，t=释放后时长
smoothstep(t) = t²(3-2t)                      C¹ 连续
钳制：累计补偿量夹在 roi_h 内（默认 300px）
门控：开火按住 + measurement_valid（量测有效，非裸 target_visible）
残差：独立亚像素结转（residual_count，与瞄准 remainder 互不污染）
延迟触发：trigger_delay_enabled + trigger_delay_ms=120（防单点误触）
```

**重做原因**（旧版病灶，业主 09-30 令「对照 yu 改」）：

- 旧版四套并跑（TTBOX 速率模型 + BB 三段查表 + 垂直修正渐变 + 开火期闭环），参数 50+ 互相打架
- 旧版**缓入 ramp 从 0 爬到 1（≈200ms）** ⇒ 最需要压的前几发反而没压，**逻辑是反的**
- 旧版残差处理是假的：`out.y = residual_; residual_ = 0;` 输出即清零 = 没结转
- 旧版闭环与瞄准 PID 抢同一执行器 ⇒ 实机「乱晃」

**yu 压枪「稳」的真正原因**：不在公式，而在**输入端永远拿不到坏框** ——  
量测门控先跑，压枪只吃有效量测。所以第二入参是 `measurement_valid` 而非 `target_visible`。

### 4.7 ★ 拟人化整形引擎（`PersonalTrajectoryShader.hpp` 400 行）— 四件套

作用在 `move_x/move_y`（int16 HID count）上、热键 Gate 之前。**在浮点位移域做**（BB 原版也是在浮点域，原版 main.lua:6010 之后才量化）。

1. **Fitts 时长模型**：`index = log2(dist/width + 1)`，`width = max(4, min_error_px×2)`；  
   `predicted = fitts_intercept_ms(120) + fitts_slope_ms_per_bit(85) × index`，压缩到 **70~220ms**
2. **速度包络**：transport 阶段加速→减速（偏峰铃形），`transport_gain=0.16`（加速峰 0~0.2）
3. **垂直向 AR(1) 随机游走抖动**：`curve_rms_px=0.8` / `jitter_amp_px=0.20` / `curve_time_constant_ms=32`（非恒定正弦，模拟人手曲线）
4. **自适应抑制 + 安全守卫**：
   - `min_error_px=18` 以下不抖动（close to target）
   - `urgent_error_px=72` 以上 → 停用整形直出
   - `urgent_speed_px_s=520` 目标太快 → 停用
   - `max_target_age_ms=18` 目标太老 → 停用
   - `capture_priority_ms=5` 捕获前几 ms 停用（等镜头稳定）
   - `direction_change_cosine=0.15` 方向突变检测
   - **安全**：输出只在 raw 基础上附加 ≤ `max_extra_px`(2.0)，且**保持与误差同向，禁止反向投影**；幅度 ≤ raw+max_extra
5. **深度融合**：`shape_f()` 浮点入口（2026-09-28，与 BB 拟人化链融合）

**区分于 PersonalMotion（倍率曲线）**：本引擎是完整移动轨迹整形。

### 4.8 ★ 抖动前馈扣除（`JitterFeedforward.hpp` 108 行）— 反直觉但正确的设计

**问题**：拟人化注入的抖动是"自己发的扰动"，它会在 `response_delay_ms`（板端实测 **51ms** ≈ 7.3 帧 @144fps）  
之后真的出现在采集画面里 ⇒ PID 把它当成"目标动了"去反向追 ⇒ **抖动被自己抹平**，闭环里还多出一串本不该有的修正。

**做法**：帧首 `advance(dt, delay)` 取出到期抖动（环形缓冲 `kCapacity=64`），乘 `gain_px_per_count` 换算 px，  
**加回** `control_x/y`（PID 之前）；帧尾 `push()` 登记本帧注入量。

**只扣抖动、不扣整条整形量**：速度包络/制动是"故意要走的那段位移"，扣掉会让 PID 以为还没到、继续加力 ⇒ 过冲。

**按 dt 累计而非固定帧数**：帧率会漂（板端 130~150），按帧数对齐会累积错位，前馈本身变成高频扰动。

零值不占位；满时丢最老；`max_px=40` 防异常值把误差顶飞。默认关。

#### ★ `hid_report_layout.cpp` — 整个注入链路的基础

**`HidField{present, bit_offset(位), bit_size, is_signed}`**（buttons 可能 3/5/8 位，X/Y 通常 8 或 16）  
**`HidReportLayout{valid, report_id, total_bits, buttons, x, y, wheel}`**  
**`HidMouseDescriptor{parsed, uses_report_ids, layouts[16]}`**

**完整解析器**覆盖 Long Item(`0xFE`) / Global(`0x0 Usage Page` `0x1 Logical Min` `0x7 Report Size` `0x8 Report ID` `0x9 Report Count`) /  
Local(`0x0 Usage` `0x1 Min` `0x2 Max`，`kMaxUsages=16`) / Main(`0x8 Input` `0xA Collection` `0xC End Collection`)；  
**每 report_id 独立位游标** `bit_cursor[rid]`；防护 `kMaxFieldBits=4096`。  
`handle_input()` 覆盖 **4 种写法**：显式列 count 个用法 / Usage Min+Max+Button 页 / 单用法配 count>1 / Button 页兜底。

**★ `hid_field_is_safe()` 两处放开（1.5.27）**：  
① `bit_size` 增加 **12** —— **罗技 G 系等大量游戏鼠标 X/Y 就是 12 位**（旧实现直接拒 ⇒ 该鼠标注入/热键全废，这是"用户反馈有些鼠标不识别"的**主力成因**）  
② **不再要求字节对齐** —— 12 位 X/Y 几乎必然跨字节（`buttons 5bit + pad 3bit` 后 X@bit8..19、Y@bit20..31）  
允许值 `{8,12,16,32}`；读写改为**通用位窗口 RMW**（HID 位序小端），**同字节里别的字段原样保留**

#### ★ `mouse_control.cpp` — 注入协议（`0x4F50` v1）

**15 个消息类型**：`PingReq/Resp`、`ErrorResp`、`MoveCmd`、`ButtonCmd`、`GetStateReq/Resp`、`SubscribeReq/Ack`、`StateSnapshot`、`ButtonEvent`、`GetConfigReq/Resp`、`SetConfigReq/Resp`  
**两个 socket**：`cmd.sock`（core→proxy 指令）/ `event.sock`（proxy→core 事件，按键）

**★ 三道安全门（`mouse_control_merge_report`，宁可不生效也绝不乱写）**：

1. 布局不可用 / 没有 X/Y → `kRejectNoLayout` / `kRejectNoXy`
2. **字段不安全**（位宽/对齐，或**与 buttons/wheel 字节区间重叠**）→ `kRejectField`
3. **长度不足**（`body_len < total_bytes()`）→ `kRejectLen`

**★ 这道门的墓碑（1.5.44 事故）**：旧代码把布局写死罗技 c53f（`X@3..4 Y@5..6 len=9`），只给**长度**加了自适应、**偏移没动** ⇒ 对现场那只鼠标（`X@1..2 Y@3..4 wheel@5`）：  
① **AI 的 Y 位移被写进 wheel 字节** ⇒ 主机每帧收到一次滚轮 ⇒ **游戏疯狂切枪**  
② **按键掩码读的是 `data[1] | data[2]<<8` = X 位移低 16 位** ⇒ 掩码恒被污染（现场实测 `0xff` = 五键全亮）⇒ **自瞄热键闸门形同虚设、「不按它也在跑」**

**★ `inject_loop()` 注入节拍（自有时钟 1ms）**：  
**为什么必须有**（2026-09-24 板端实测）：物理报告只在"用户在动鼠标"时才来，  
现场 dongle 静止时 IN 端点报告率 **0/s**（移动时 105~170/s）⇒ 只靠搭车的话  
**手一停准星就完全不动、手一动又把积压一次性抖出来（瞬移）**（复算：单次投递最大 39.7 count ≈ 26px）。  
每拍：`pending` 全 0 且无按键变化 ⇒ **快路径退出**（否则每 1ms 都要抢 `layout_mutex`）→ `take_step()` → 发报告。  
**按键变了就必须发**（这份报告 X/Y=0 但带新的按键状态，否则 AI 扳机的点击永远到不了主机）。  
**★ sink 调用必须持锁到返回** —— `terminate_eps` 的「先摘出口再 delete 队列」只对还没取到指针的迭代有效，  
已取到指针的本拍会与 delete 并发（**UAF**）。  
**★ 投不出去就把这一拍退回挂起量（不丢位移）**，下一拍重试。

**★ `cmd.sock` 安全加固**：

- **不 unlink 正在服务的 socket**（先 probe connect，成功则拒绝替换）
- `chmod 0660`（此前 0666 全局可写，任意本地用户可注入鼠标指令）
- **★ `cmd_peer_allowed()` 内核级对端身份校验**（`SO_PEERCRED`，内核填无法伪造）：只放行 **root / 同 uid / 同主组(ttbox)**。  
  此前唯一防护是文件权限 ⇒ 同组用户、以及任何拿到 ttbox 组身份的进程都能发 `SET_CONFIG + apply_now`  
  把 usb-proxy 直接 `_exit(0)` 杀掉并把 `gadget-config.json` 写坏（重启后 Windows 无法枚举）

**★ `persist_gadget_config()` 原子落盘**（tmp→`fflush`+`fsync`→`rename`）。  
原实现直接 trunc 原文件再流式写，中途崩溃/断电/ENOSPC 留半截 JSON ⇒ 下次开机解析失败 ⇒ 设备无法枚举（用户视角"盒子坏了"）。

**★ `decode_config_payload()` 越界即整包作废** —— 原实现截断时静默返回却继续解析且**恒返回 true** ⇒  
畸形 SET_CONFIG 会把配置写成一堆空字段，重启后设备无法枚举，且 "bad set-config payload" 永远走不到。

**★ `add_pending()` 钳位+饱和**：`kMoveStepLimit=32767`（单次）/ `kPendingLimit=1<<20`。  
原实现 `fetch_add` 无钳位 ⇒ ① int32 溢出是**未定义行为** ② 累积无限增长，表现为鼠标"飞"出去几十秒回不来。

#### `usb-proxy.cpp` main 流程

`setvbuf(stdout, NULL, _IOLBF, 0)` **行缓冲**（systemd 下 stdout 是 socket ⇒ glibc 默认全缓冲 4KB 才刷，  
排障时日志停在半截 —— 1.5.56 事故里 active fetch 的失败日志就这样被吞了）→ 信号 handler（第一次置 stop flag，第二次 `exit(1)`）→  
解析 18 个选项 → 加载 injection.json/config.json → `mouse_control_start` → `usbproxy_mlockall` → `connect_device` 循环 →  
**探测物理设备速度** → `setup_host_usb_desc` → **★ bInterval 单位换算** → `usb_raw_open` → `usb_raw_init(HIGH)` → `usb_raw_run` →  
端点重映射（可选）→ `ep0_loop`（阻塞）→ 清理

**★ bInterval 单位换算（容易错）**：`bInterval` 单位**随速度域变**（全速/低速是毫秒，高速是 `2^(n-1)` 个 125µs 微帧）。  
物理设备跑全速而 gadget 以高速连电脑时，描述符必须换算，否则一个"1ms"端点在电脑侧被解释成 125µs（**8kHz，语义差 8 倍**）。  
规则 `HS = 2^(bInterval-1) × 125µs`，即 **FS bInterval=1 (1ms) → HS bInterval=4**。  
2026-09-27 把**低速一并纳入**（大量廉价 2.4G 接收器是 Low Speed，此前漏换算同病）。  
旧代码**只换算 ISO** ⇒ 满速鼠标在高速侧被当成 8kHz。

#### `proxy.cpp` 的三次血泪教训（写在这里别再犯）

1. **1.5.56：`ec49c73` 在 ep0 同步发 class `GET_DESCRIPTOR(Report)`** ——  
   Compx Nearlink Dongle 373b:10c9 实测**一律超时且控制端点被打死**（3 接口 × 3 种 wLength 全 -7）⇒  
   电脑枚举超时、1.6s 一次 reset 风暴后放弃，**UDC 恒 default、鼠标彻底死**。  
   → 改为后台 `hid_layout_worker`，**绝不阻塞 ep0 热路径**；兜底 = **hidraw 抄底（零 USB 请求）→ 每接口至多 1 次 class → 10 轮无进展 fail-open 开门**
2. **1.5.58：quirk 固件对 usbfs 上下文的该请求不应答且会被打死**（整设备掉总线）⇒  
   主机每次枚举都要 ⇒ 每次都伤害设备 → **已有内核缓存就直接答主机**（`served_from_hidraw_cache`）
3. **1.5.59：`served_from_hidraw_cache` 绝不从 `control_data` 拷** ——  
   它是 `new[]` 出的**未初始化缓冲**，拷进去会把刚写好的描述符覆盖成堆垃圾 ⇒ 板端实测描述符变乱码 ⇒ 布局被冲掉、注入静默失效。  
   → 加**脏描述符保护**：新描述符合不出任何可用报告、而旧布局本来可用 ⇒ 视为脏数据，原样保留

**★ 中断 IN 环形缓冲（1kHz 的关键）**：注释实测 —— **1 个在飞传输 → ~2.00ms/报告（500Hz）；2+ 个 → ~1.00ms（1000Hz）**。  
主机控制器每帧走一次 periodic list，端点在该瞬间没有排队传输就丢一帧。  
`interrupt_ring`：`INT_RING_DEPTH=8` / `QUEUE_MAX=64` / `interrupt_ring_next()` **100ms 有界等待**（鼠标只在移动时上报）

- **每 2s 打速率自诊断**（空闲时也打 "0 reports"，否则看着像"代码没生效"）。

**★ `terminate_eps()` 三阶段**：① 置 stop flag + `pthread_kill(SIGUSR1)`（打断阻塞 ioctl 无副作用）  
② `pthread_join` ③ **先摘注入出口**（`mouse_control_clear_inject_sink`，**绝不能让注入节拍线程拿到悬空指针**）→ `usb_raw_ep_disable` → delete

**★ quirk 固件保护（1.5.61/1.5.63）**：`reset_device_before_proxy` **默认 false** ——  
quirk 固件（星闪接收器 373b:10c9）扛不住一次 usb reset（日志特征 `libusb_reset_device() failed: Entity not found`，  
之后 lsusb 再也看不到，**只能拔插**）。无条件 reset 会把物理鼠标打死。

**★ 启动脚本三级鼠标判定（避免 report protocol 鼠标永久不被识别）**：

- **R1** `bInterfaceClass==03 && bInterfaceProtocol==02`（传统 HID boot 鼠标）
- **R2** `udevadm info --query=property` 含 `ID_INPUT_MOUSE=1`
- **R3** `/sys/class/input/eventN/device/capabilities/rel` 非 0
- 排除 `bDeviceClass==09`（Hub/根 Hub）
- **放宽原因**：现代复合游戏鼠标走 report protocol（sub/proto 都是 00），实机 **MCHOSE A7 V3 Pro+（3837:1014）三个 HID 接口全是 00/00** ⇒  
  旧实现只认 proto=02 永不匹配 ⇒ 无限"等鼠标" ⇒ 不建 socket、gadget 不绑、UDC 恒 not attached、  
  core 的 PhysicalMouseReader 也连不上（**透传整体不可用**）
- `usb_dev_of_input()`：**向上走到最近的含 `idVendor`+`idProduct` 的目录再比相等**  
  （不能用设备路径做前缀匹配 —— Hub 是鼠标的祖先，前缀匹配会把父 Hub 也判成鼠标）
- `mouse_scan_report()`：等待期每 10s 打全量接口诊断表（区分"没插鼠标"与"插了但被判成非鼠标"）

## 17. 已知实现缺陷（审核中确认，有测试钉住现状）

| 缺陷                           | 位置                                                                                                                         | 说明                                                                                                                                                                                                                  |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **僵尸 track 不回收**             | `TargetSelector.cpp` 三处 `lost_frames++` 全包在 `if (t.active)` 内                                                              | track 一旦 `active=false`，`lost_frames` 冻结 ⇒ `trim_tracks` 的 `!active && lost_frames>track_buffer_frames` 永不成立。不泄漏（`max_tracks=64` 兜底 pop_back），但 track 表长期满额，僵尸条目持续参与关联竞争。**修它必须同步改 `test_target_selector.cpp` 的断言** |
| **硬件裁剪 ioctl 不生效**           | `V4L2Capture.cpp:285`                                                                                                      | 审计 Q4，唯一核心链路 bug，走专项通道                                                                                                                                                                                              |
| **`ModelRuntimeState` 是假覆盖** | `model/ModelRuntimeState.hpp`                                                                                              | 8 个方法生产引用 = 0，只有测试在用 ⇒ 测试全绿但保护不了生产。真门在 `ApplicationRuntime.cpp::switch_active_model_runtime()` 首帧门槛                                                                                                                 |
| **析构里调虚函数**                  | `V4L2Capture`（调 stop/close）、`HidRuntime`（调 stop）                                                                           | 当前无派生类故不触发；派生就会漏资源（V4L2 漏 dma-buf fd ⇒ 板端重启后 `/dev/video0` 打不开）。`LocalHidBackend` 标 `final` ⇒ 天然免疫                                                                                                                  |
| `search_radius_px` 默认 0      | `TargetSelectorConfig`                                                                                                     | ⇒ `clipped_by_crop` 直接 `return false`，**贴边剔除整条路径静默失效**。生产由 AimThread 填 `min(capture.w,h)/2`（板端 320）。⚠ 任何直接调 `TargetSelector` 的新代码**必须自己填这个字段**                                                                      |
| **死接线**                      | `RecoilController::update()` 的 out.x 恒 0 / `drift_*` 已删字段 / `pull_curve.jitter_px` 零消费 / `aim_profiles[0].fov_scale=1` 恒 1 | 「开关没反应」先查这张表                                                                                                                                                                                                        |
| `predict` 上限不同源              | 标定 0.35 vs core 1.0                                                                                                        | 标定面板与 core 不同源                                                                                                                                                                                                      |
