## 3. 动手前必须先定的三件事

### 第一件：板端 release 树布局要不要跟着变？

这是**分水岭**，决定后面所有工作量。

**选项 A（推荐）**：仓库内部重排，**板端 `/opt/ttbox/current/` 布局保持不变**。
- 好处：`deploy/systemd/*.service` 的 `ExecStart=/opt/ttbox/current/plugins/web/bin/ttbox-web` 这些**一行都不用改**；OTA、安装脚本、兼容软链、板端已验证过的东西全部不受影响；搬完可以只在本机验证。
- 代价：仓库源码树和板端产物树长得不一样（源码 `board/src/web/`，产物还是 `plugins/web/`）。需要用 `pack_manifest.txt` 做映射。
- 具体做法：`pack_manifest.txt` 里把来源路径改成新的，**目标路径（板端落点）保持旧的**。这份清单本身是按「仓库根相对路径」写的，只要加一层映射就能做到。

**选项 B**：板端布局也改成 `current/{bin,board,...}`。
- 代价：7 个 systemd unit 的 ExecStart、`ttbox_ota_updater.py`、`ttbox_release_install.sh`、`ttbox_fhs_init.sh`、`ttbox.sh`、`ttbox_doctor.sh` 的路径断言、板端两个兼容软链（`/opt/ttbox/plugins`、`/opt/ttbox/scripts`）全要改，而且必须上板验证。**至少多出一个板端往返周期，且验收窗口只有一次。**

我建议 A。等结构稳定、下一次大版本再考虑 B。

### 第二件：`pipeline/` 那 7 个子目录，现在就重排吗？

重排不是搬位置，是**重新分组 + 拆文件**：
- `rknn/`（9 文件）要拆成 `preprocess` / `inference` / `decode` 三份；
- `mouse/`（30 文件）要拆成 `selector` 和 `control` 两类；
- `aim/` 要并入 `control/`；
- `core/src/common/` 要拆共享与私有。

动的是**核心链路**（7 段里有 6 段），按已拍板的原则「原样搬、行为等价优先」，拆的过程中不能改算法。
拆完必须逐段做**离线回放对照**（同一份 `_det.csv` 输入，新旧输出差异必须为 0）。

**选项 A（推荐）**：分两步——先整棵 `core/src/` 搬到 `board/src/core/`（内部结构不动，行为零变化，ctest 必须仍 41/41），**重排单独做第二批**，一批拆一段，每段带回放证据。
**选项 B**：一次到位，搬的同时重排。风险是「搬错了」和「拆错了」混在一起，出问题无法归因。

我建议 A。理由跟你第一阶段定的「别一边搬一边拆」是同一条。

### 第三件：`web/`（Vue3）和 `cloud/` 现在建吗？

- `web/` 建目录就等于启动前端重写（现状 13446 行单文件 → Vue3 工程）。**建议先只在目标态里占位，不建工程**，等板端结构稳了单独排期。

## 5. 硬约束与风险（动手前逐条过）

1. **`core/CMakeLists.txt` 的源文件是显式列表，不是 glob。**
   第 120-184 行是 `CORE_SOURCES`，第 533-591 行是 `TEST_SOURCES`。移动任何一个 `.cpp` 都要手改这里。漏一个就是链接错误。这是批 1 最大的体力活。

2. **`-ffile-prefix-map=${TTBOX_SOURCE_ROOT}=.` 会让产物字节变化。**
   `core/src/...` 变成 `board/src/core/...` 后，编进 `.rodata` 的 `__FILE__` 字符串跟着变。CMakeLists 第 104-117 行的注释明确写了纪律：**指纹锚要「保留旧锚 + 追加带时点的新锚」**，不许偷删旧记录。所以「二进制哈希变了」是**预期行为**，不是搬错了——但要能解释清楚。

3. **`TTBOX_PROJECT_ROOT` 被编进目标码**（`Application.cpp` 的 `kDefaultConfigPath`），交叉编译不显式传就 `FATAL_ERROR`。搬 `core/` 后 `${CMAKE_CURRENT_SOURCE_DIR}/..` 的推导默认值会变，但出货构建永远显式传 `-DTTBOX_PROJECT_ROOT=/opt/ttbox`，所以**只要构建脚本照旧传值就不受影响**。别忘了检查。

4. **`deploy/pack_manifest.txt` 是出货白名单，被两个地方读**（`ttbox_fhs_init.sh` 的 `sync_tree`、`ttbox_pack_ota.sh`）。它按「仓库根相对路径」写。搬 `plugins/`、`usbproxy/`、`scripts/` 就必须同步改这份清单，否则**装机树和 OTA 包会同时缺文件**。
   若采纳 §3 第一件事的选项 A，这里要做的是「来源路径改新、落点保持旧」，需要给 `pack_manifest.txt` 加一层来源→落点映射语义（现在它只有一列）。

5. **`deploy/systemd/*.service` 的 ExecStart 指向板端路径**（`/opt/ttbox/current/...`），不是仓库路径。只要 release 树布局不变，**unit 一行都不用改**。这是选项 A 的最大好处。

6. **`ttbox-web.py` 的 `sys.path` 硬编码了层级深度。这是批 1 最容易漏的一条。**
   实测 `plugins/web/bin/ttbox-web.py:40-41`：
   ```python
   sys.path.append(str(Path(__file__).resolve().parents[3]))    # 仓库根 → 为了 import ttbox_motion
   sys.path.insert(0, str(Path(__file__).resolve().parents[1])) # plugins/web → 为了 from lib import
   ```
   当前层级：`parents[0]=bin`、`[1]=web`、`[2]=plugins`、`[3]=仓库根`。
   搬到 `board/src/web/bin/` 后变成：`[1]=web`、`[2]=src`、`[3]=board`、`[4]=仓库根`
   ⇒ **`parents[3]` 必须改成 `parents[4]`**；`parents[1]` 不用动（只要 `lib/` 跟着 `web/` 一起走）。
   不改就是 `ttbox_motion` 导入失败、`ttbox-web` 直接起不来，而板端表现为「网页打不开」，很容易误判成别的问题。

   顺带一提：同文件 `:34-39` 那条「必须用 append 不能用 insert(0)，因为 `/opt/ttbox/platform/` 撞标准库」的约束，
   **在 `platform/` 删掉之后就自动消失了**。删 `platform/` 因此多了一个收益，建议批 1 一并处理。

7. **`scripts/ttbox_build_release.sh` 有产物路径锚断言**（A4①：产物内构建机绝对路径必须为 0）。搬完要重跑确认。

8. **门禁脚本里有大量路径常量。**
   `scripts/ttbox_conventions_gate.sh`（628 行）、`scripts/ttbox_phase1_gate.sh`、`scripts/phase1_longfile_registry.txt`（58 个文件路径）、`scripts/phase1_gate_baseline.txt`。搬完这些引用全部要更新，否则门禁会误报。

9. **板端有两个兼容软链**：`/opt/ttbox/plugins`、`/opt/ttbox/scripts` 指向 `current/*`。选项 A 下不受影响。

10. **`plugins/web/lib/paths.py` 与 `core/src/common/Paths.hpp` 是路径单点真源**，且两处要**同值**（有门禁断言）。搬目录时这两个文件本身的**内容**不能乱改，只改引用它们的代码路径。
