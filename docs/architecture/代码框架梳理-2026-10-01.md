## 0. 这份文档干什么用

现有的 `RK3588_CURRENT_AUDIT.md` 回答的是「哪儿坏了」——它是一份问题清单。
这份回答的是「东西在哪、怎么连的、改哪」——它是一份地图。

两句话的区别：
- 审计说：`V4L2Capture.cpp:285` 的 ioctl 不生效（Q4）。
- 这份说：采集段在 `core/src/capture/`，只有 3 个文件，入口是 `V4L2Capture`，被 `CoreRuntime` 在 `:45` 创建，改它不会碰到别处。

用法：

| 你想干什么 | 翻哪一节 |
|---|---|
| 改一个功能，不知道动哪个文件 | §7 功能 → 文件映射表 |
| 搞清楚这几块谁依赖谁 | §9 依赖方向 |

| 发现本文与审计数字对不上 | §12 修正表 |

**一句话概括这个系统**：HDMI 线进画面，AI 找出目标，PID 算出该往哪推鼠标，通过 USB 假装成一个鼠标把动作送进游戏机。四个常驻进程分工，C++ 管实时链路，Python 管面板和流程。

## 1. 系统全貌

### 1.1 五个进程

板端常驻 4 个（实测 `ps`），都是 systemd 直管（PPID = 1）：

| 进程 | 身份 | 干什么 | 端口 |
|---|---|---|---|
| `ttbox_core_main` | root:ttbox | C++ 实时核心：采集→识别→瞄准→输出，另有授权与 IPC 服务 | `/run/ttbox/core.sock` |
| `usb-proxy` | root | C++ 注入代理：把「物理鼠标」和「AI 动作」合成后交给游戏机 | `/run/ttbox-mouse-passthrough/{cmd,event}.sock` |
| `ttbox-web.py` | ttbox | Python 面板：网页 + 全部业务 API + 写特权任务 | `0.0.0.0:8000` |
| `ttbox-preview.py` | ttbox | Python 预览：独立 MJPEG 流，不占核心线程 | `127.0.0.1:8001` |

辅助的 3 个（非长驻）：

- `ttbox-edid.service`（oneshot）——开机注入 EDID，让采集卡认显示器。
- `ttbox-time-guard.service`（oneshot）——开机抬系统时钟。**脚本不在仓库，只在板端 `/usr/local/sbin/`**（审计 Q24）。
- `ttbox-ota.path` → `ttbox-ota.service`（root oneshot）——面板往 `/var/lib/ttbox/ota/jobs/` 丢一个 json，systemd 拉起 root 更新器。

### 2.3 装配三层

```
main.cpp (50 行)
  └─ Application (2265 行)   ← 什么都管：CLI、风扇、调频、配置、授权、IPC、模型、主循环、看门狗、冒烟
       └─ CoreRuntime (549 行)  ← 只管「拥有并启停」采集/推理/瞄准/预览
            ├─ V4L2Capture
            ├─ WorkerPool (含 Preprocess/RKNNEngine/DecodeNMS)
            ├─ AimThread (含 TargetSelector/Pid1Controller)
            └─ PreviewModule
```

关键分工事实：
- `CoreRuntime` **不读配置、不碰授权**——给它参数它就启停。这是好设计，要保住。
- `Application` 是唯一的「什么都知道」的类，2265 行里塞了 8 种职责。**这是全项目最该拆的文件之一**，但按「原样搬」原则，第一阶段不拆。

### 2.4 依赖方向

干净的：

```
app → runtime → {capture, rknn, aim, output, preview, input, model, pipeline, common}
aim → {mouse, output, model, pipeline, common}
rknn → {capture, rga, model, mouse, detector, pipeline, common}
```

有一条**目录级循环**：

```
model ⇄ rknn
  model → rknn：model/Decoder.hpp:19、model/RuntimeProfile.hpp:22、model/ModelAdapter.hpp:18
  rknn  → model：rknn/DecodeNMS.hpp:22、rknn/Detector.hpp:9-10、rknn/WorkerPool.hpp:29-32
```

不是致命问题（C++ 头文件互相包含很常见），但它是「模型管理」和「推理引擎」纠缠不清的直接证据。想换推理后端时会立刻撞上。

`common/` 被所有层包含，自己只包含标准库和自身——**这个方向必须守住**，一旦 `common/` 开始包含业务类型，分层就塌了。

## 4. 注入层（`usbproxy/`）

独立 C++ 进程，19 个 C++/H 文件约 7387 行。

**它才是真正把鼠标动作送进游戏机的地方。** core 无论用哪种输出后端，都只是上游指令源。

数据流：

```
物理鼠标 ──libusb 独占──> proxy.cpp 端点转发线程 ──┐
                                                  ├─> usb_raw_ep_write ──> OTG ──> 游戏机
core ──cmd.sock(MOVE/BUTTON)──> mouse_control 合并 ─┘
```

两条通道：
- **cmd.sock**（下行）：core 的 `MouseControlClient` → usb-proxy。自研 0x4F50 协议，`AF_UNIX + SOCK_SEQPACKET`，8 字节头（magic/version/type/request_id），连接前 `SO_PEERCRED` 校验。
- **event.sock**（上行）：usb-proxy 每 100ms 推 `STATE_SNAPSHOT`（按键位图），物理按键变化时推 `BUTTON_EVENT`。core 的 `PhysicalMouseReader` 订阅，用途是给瞄准线程做热键门控。

输出后端有两套，由配置 `output_backend` 选（出厂默认 `usb_proxy`）：
- `usb_proxy` → `UsbProxyBackend` → 写 cmd.sock（**出货在用**）
- `local_hid` → `LocalHidBackend` → 直接 `write` 到 `/dev/hidg0`

`usbproxy/tests/*.exe` 两个预编译二进制不是垃圾——`Makefile:49-60` 的 `make test` 会构建并运行它们（源文件 `test_hid_layout.cpp` 406 行、`test_inject_clock.cpp` 270 行）。**但它们不该入库**（违反「禁制品入库」，审计 Q 系列已记）。

## 7. 数据流

### 7.1 一帧画面的一生

```
HDMI 输入 → [V4L2Capture] mmap 拿 dma-buf fd
   ↓
[RGA] im2d crop + resize 到模型输入尺寸（dma-buf 直接进，零拷贝）
   ↓
[RKNNEngine] 绑定输入 → NPU 跑 → 拿原始输出张量
   ↓
[DecodeNMS] 按模型布局解成框 + 置信度 → NMS
   ↓
[DetectionGeometryFilter] 剔掉几何不合理的框
   ↓
[WorkerPool] 打包成 AimTargetTask → 塞进 AimTargetMailbox（覆盖式）
   ↓
[AimThread] 取最新任务
   ├─ [TargetSelector] 选一个目标（track_lock → rect_lock → score 三层）
   ├─ [AimPointProfile] 算出该瞄框内哪个点
   ├─ [Pid1Controller] X/Y 各算一次输出
   ├─ [OneEuroFilter/Jitter/Recoil/...] 一串后处理
   ├─ [OutputGate] 放行判定（授权/开关/热键）
   └─ [IHidOutput] → usb-proxy cmd.sock → USB → 游戏机
   ↓
[PreviewModule] 另起线程，把帧编码 MJPEG 给预览进程
```

### 7.2 配置怎么下发

```
网页改参数 → PUT /api/config (ttbox-web.py)
   → lib/ipc.py 发 SET_CONFIG
   → core 的 IpcServer 收 → ConfigManager 写 config.d 的 10-device.json
   → 生效
```

引擎端有**三级配置来源**：`/etc/ttbox/config.d/00-factory.json`（出厂基线，升级整体替换）→ `10-device.json`（设备层，升级不覆盖，Core 唯一写回目标）→ 运行期内存。深合并。

**现存问题**：客户端数据实际分两处——预设在 `/opt/ttbox/presets`，而 `/var/lib/ttbox/presets` 建了目录没人写。OTA 的「不碰客户数据」只保护 `/var/lib/ttbox`，保护不到 `/opt/ttbox` 里的那份。这是审计 Q23，第一阶段必须统一。

### 7.3 命令与状态

- **命令**：网页 → `lib/ipc.py` → `core.sock` → `IpcServer`（15 个命令）→ 各自处理器。
- **状态**：网页轮询 `GET_STATUS` 拿 JSON（running / runtime_running / license / metrics），前端 1500ms 一次。
- **没有** WebSocket/SSE，`/api/events` 是个空壳（审计 Q21）。前端只能轮询，这是架构决定的，不是懒惰。

## 8. 依赖与边界问题

### 8.1 违反「一个文件只属一个进程」的地方

规矩在《代码书写规矩·技术版》§3。现状违反：

1. `plugins/web/bin/ttbox-web.py` 直接 `subprocess` 跑 `scripts/edid/*.sh`、`hostnamectl`、`systemctl reboot`——**跨进程直接指挥**，且以 ttbox 身份干 root 的事。
2. `ttbox-web.py` 里有 3 处硬编码绝对路径（`:3824/:3854/:4765`），绕过自家 `paths.py`（审计 Q20）。
3. `ttbox_motion/` 同时被网页进程 import 和 `core/tools/pid_sim/tune_check.py` import——跨进程共享算法代码，但没走 `common/`。

### 8.3 构建目录——5 个里有 4 个指向别的仓库

这是个容易踩的雷：

| 构建目录 | 源树 | 生成器 | 有产物 |
|---|---|---|---|
| `build-aarch64-t148/` | `/mnt/c/ttbox-local/core` | Ninja | 有 |
| `build-aarch64-t148-repro/` | `/mnt/c/ttbox-local/core` | Ninja | 有 |
