## A. 矛盾项

### A1 板端先做 vs 停旧接口 / 还要能测心跳 【老板】

- **冲突双方**：`#149`（开发顺序：先板端重构…最后云端补全）+ `§0`（云端已是"已有系统"）+ `#126`（云端接口尽量沿用现有） **︎vs** `#124`（旧版云端接口停掉，旧版设备 1 小时后停用）+ `#160`（板端重构期间旧接口停掉）。
- **冲突点**：
  1. 全部在线设备的心跳走**同一个**云端（审计§16.4：云授权端点 + `TTBOX_LICENSE_SERVER`）。接口一停，现有设备在 1 小时内进入停用态。
  2. 板端只有 1 台（`#164`）。旧接口停掉后，新版心跳/激活**没有任何真实端点可测**，只能打桩，等于"上线即首测"。
  3. 云端排在最后做（`#149`），意味着新契约在板端重构期间**根本不存在**，`#160` 说的"按新契约预留"缺少契约。
- **可选解法**：
  1. **新旧并行 + 定切换日**：v1 接口原样不动，v2 契约先冻结、云端同期并行上线；切换日 = `#148`"全部做完一起发"那天，届时才停 v1。
  2. **立即停 v1**：接受现有设备全停 + 板端重构期无真实端点，全走 mock。
  3. **云端按版本分流**：设备上报版本，旧设备永久走 v1、新设备走 v2（等于永不互斥，只是运维成本略增）。
- **建议**：解法 1（并可在 3 上加深，做成分流以免切换日出事）。
- **理由**：`#164` 只有 1 台板子，不给它一个真端点，"重构完成"这个结论拿不到证据；`#156` 也要求发现冲突就停下来问，而不是硬做。停机窗口是商业决定，必须老板定日期。

### A9 内存盘固定 1G vs 内存不设上限 【老板】

- **冲突双方**：`#80`（内存盘固定划 1 GB） **vs** `#81`（内存上限不定，能用就行）。
- **技术澄清**：tmpfs 是**懒分配**——"划 1G"是设 `size=` 上限，**不预占物理内存**。所以两条并非在"占用"上冲突，只在**口径**上冲突。真正风险在：8G 内存、**swap=0**（审计§6），核心程序又要在内存盘执行（`#97`），若帧缓存/日志/程序镜像同挤 tmpfs，OOM 风险实存。
- **可选解法**：
  1. 1G = 上限（不预占）+ 水位监控 + OOM 兜底。
  2. 1G = 开机强制预占（无意义，徒增 OOM 概率）。
  3. 取消内存盘。
- **建议**：解法 1。
- **理由**：既满足 `#80` 的字面，也不与 `#81` 打架。需老板认"1G 是上限不是预占"这个口径。

  2. 承认内部全开，删掉 `#1` 里"防内部泄露"这个目标。

### A13 日志放内存省卡 vs 日志要能导出 / 崩溃取证 【老板】

- **冲突双方**：`#92`（SD 卡少写：日志、临时文件尽量放内存）+ `#80`（内存盘 1G） **vs** `#62`（网页一键导出 ZIP）+ `#60`（诊断包，设备上不长期保留）+ `#88`（崩溃只留日志）。
- **现状事实**：根分区 4.5G 已用 3.2G / **75%**（审计§6）；板端已有垃圾残留：`cloud_session.json.tmp.*` **×37**、`V1.0.17.ota.staging` **12M**、`_incoming/*.rknn` ×5（审计§22.4 / Q1/Q2/Q31/Q32/Q33）。所以"少写卡"的动机成立。
- **冲突点**：日志放内存 = 断电即失，而最需要日志的恰是断电/死机之后。
- **可选解法**：
  1. **分级**：崩溃 / 错误 / 客户操作 **即时写卡**；流水日志进内存 + 定时落盘。
  2. 全内存（售后无证据）。
  3. 全写卡（违背 `#92`，且要先解决 Q1/Q2 残留否则加剧磁盘压力）。
- **建议**：解法 1，并**先修 Q1/Q2**（不然"少写卡"省下来的空间被 tmp 泄漏吃掉）。
- **理由**：`#60`/`#62` 是售后能力的下限，`#92` 是寿命优化，二者不冲突——只要按级别分流。

### A14 Windows 上点一下跑测试 vs 中文路径假失败 / 交叉编译环境 【老板】

- **冲突双方**：`#162`（构建测试位置：Windows 电脑上手动点一下跑）+ `#163`（Windows 跑治理层测试，板端跑核心链路测试） **vs** 事实约束。
- **事实约束**：
  1. 工作区路径含中文（`G:\WORKBUDDY工作区\...`），宿主 ctest **恒少 2 例假失败**（审计§18.1 已标注：中文路径下 `std::ifstream` 打不开绝对路径）。
  2. aarch64 出货二进制必须走 **WSL 交叉编译**（`deploy/cmake/toolchain-aarch64.cmake`，审计§18.1/§18.2），Windows 本机跑不了。
  3. 出货向量**顺序敏感**：`-DCMAKE_SYSROOT` 必须在 `-DCMAKE_TOOLCHAIN_FILE` **之前**，顺序反了 `vector_hash` 变化（审计§18.2）。
- **可选解法**：
  1. **固化一套 ASCII 路径的宿主构建目录 + WSL 交叉链，封装成一键脚本**（推荐）。
  2. 照旧手工点，接受每次 2 例假失败人工忽略。
  3. 全部搬到板端跑（但只有 1 台板子，会占死，且与 `#164` 冲突）。
- **建议**：解法 1。
- **理由**：这是**环境准备工**，不是技术难关，但需要老板认可"要花半天到一天把环境配好"这段时间，否则会被当成"卡住了"。

### A15 签名私钥放云端普通文件 vs 云端不备份 【老板】

- **冲突双方**：`#100`（签名私钥放云端服务器，自动签名）+ `#101`（**暂时存普通文件**，权限只有 root 可读）+ `#132`（云端数据库不备份）。
- **现状事实**：仓库内**只有公钥**（审计§18.2；另有 R3 两处公钥副本：`deploy/keys/` 与 `tools/ota/keys/`）；私钥仅云端一份，无副本、无备份。
- **风险链**：私钥丢失 ⇒ 无法再签任何新版本 ⇒ `#113`"云端只放最新包、客户点更新"整条作废 ⇒ 客户设备永久停在最后一版，只能整机重烧（`#118` 单系统 + `#119` 不能回退）。这是全项目**单点风险最高**的一条。
- **可选解法**：
  1. **私钥离线异机备份（离线介质或第二台机器）+ 定期恢复演练**。
  2. 照旧只放云端。
  3. 另存一份在老板手里。
- **建议**：解法 1。
- **理由**：云端不备份（`#132`）本身可行，但签名私钥不属于"数据库"，不该被 `#132` 顺带覆盖。要不要多存一份是老板的决定。

### A16 单系统断电重烧 vs 升级失败重试 3 次 / 继续用当前版本 【老板】

- **冲突双方**：`#118`（单系统，升级断电坏了重新烧录 SD 卡）+ `#119`（不能回退旧版） **vs** `#115`（下载失败自动重试 3 次）+ `#116`（安装失败重试最多 3 次，**仍失败继续用当前版本**）。
- **冲突点**：`#116` 要求"失败后还能用当前版本" ⇒ 安装过程不能破坏正在运行的那一份 ⇒ 需要"另一份兜底"，与"单系统"和"不能回退"的字面口径打架。
- **技术事实**：审计§19.2 现有 7 步 OTA 已经这么做（展开到 `releases/<ver>.ota.staging/` → 全量复验 → **原子发布** 切 `current` 软链）。⇒ 结论是"把现有做法写进方案"。
- **可选解法**：
  1. **明确"单系统"= 只有一份可运行版本，但升级走"先展开新版本到新目录 + 原子切换"，失败即保持旧目录不动。**
  2. 原地覆盖安装（则 `#116` 无法满足，且断电必砖）。
  3. 改双系统 A/B（违背 `#118` / `#90`）。
- **建议**：解法 1。
- **理由**：`#118` 描述的是**断电后果**，`#116` 描述的是**失败策略**，两者只有在"原地覆盖"时才会真冲突。用现有的原子切换即可同时满足。
