## 三、逐条处置方案

### S1 设备上存在授权签发私钥（最高，安全）

**现象**

| 位置 | 内容 |
|---|---|
| `/root/ttbox-src/tools/license/.testkeys/ttbox-license-2026a.priv.pem` | 119 B，与 core **内嵌**的 `ttbox-license-2026a` 公钥**配对** |
| `/root/ttbox-src/tools/ota/.testkeys/ttbox-ota-2026a.priv.pem` | OTA 2026a（现役已换 2026b，危害有限，但同样不该在设备上） |
| `/tmp/dg_cert.pem`、`/tmp/dg_key.pem` | 上一轮 OTA 联调的自签 CA 残留 |
| `/root/ttbox-src/` | 88 MB 完整源码副本，属主 `197108/197121`（Windows 侧 uid），scp 上去的调试遗留 |

**仓库侧已核实**：`git ls-files` 中不存在任何 `*.priv.pem` / `.testkeys` 文件。**这不是入库问题，是设备/镜像问题。**

**处置**

业主先回答一个问题：**出厂镜像是不是以 192.168.0.104 为模板？**

- 若「是」→ 必须清 + 轮换，两步都不能少：
  1. 清残留：`rm -rf /root/ttbox-src && rm -f /tmp/dg_cert.pem /tmp/dg_key.pem`
  2. 轮换 license 密钥对：生成 2026b 新密钥对 → 私钥入本机固定加密目录（与 ota 2026b 同规格，口令加密）→ core 重新编译内嵌新公钥 → **旧 2026a 签发的所有授权卡全部失效**，需通知渠道并准备补发
  3. 同步 `tools/license/` 的 key_id、`deploy/keys/` 的公钥、相关文档
- 若「否」→ 只需清残留（第 1 步），并在出厂镜像构建流程里加断言。

**无论走哪条都要加的护栏**：新增出厂自检，扫镜像内 `/root /tmp /opt /etc` 下的 `*.pem` / `.testkeys` / `id_rsa`，命中即 FAIL。建议挂在 `scripts/ttbox_release_verify.sh` 里，与现有出货校验同一入口。

**验证**：`find / -xdev \( -name '*.priv.pem' -o -name '.testkeys' -o -name 'id_rsa' \)` 输出为空。

### S2 卸载不干净（阻塞）

**根因**：`scripts/ttbox_uninstall.sh:46`

```bash
rm -f /etc/systemd/system/"${UNITS[@]}"
```

bash 里这个双引号**只作用于数组的第一个元素**，其余 8 个退化成相对路径被静默忽略。板上实测：同名命令 9 个文件名进去，只删掉 1 个，剩 8 个。

**改法（三处）**

| 行 | 现状 | 改成 |
|---|---|---|
| 46 | `rm -f /etc/systemd/system/"${UNITS[@]}"` | `for u in "${UNITS[@]}"; do rm -f "/etc/systemd/system/$u"; done` |
| 22 | `DIRS=(/opt/ttbox /etc/ttbox /var/lib/ttbox /var/log/ttbox /run/ttbox)` | 补两项：`/run/ttbox-mouse-passthrough`（板上实测存在，含 `cmd.sock` / `event.sock`）、`/lib/firmware/ttbox`（含 `hdmirx_edid.bin`） |
| 5 | 注释「7 个 unit（含 ttbox-ensure.timer 与 ttbox-ota.path/service）」 | 改为「9 个 unit」，且 `UNITS` 数组本来就是 9 条 |

顺带把 `:27` 的 plan 输出（`rm -f /etc/systemd/system/{...}` 花括号表达式）改成逐条打印，跟实际执行对齐——dry-run 的输出必须能当清单用。

**验证**（注意这脚本不可逆，验收前先 `ttbox.sh backup`）

1. 板上确认 `ls /etc/systemd/system | grep -c ttbox` 当前 = 9
2. `bash ttbox_uninstall.sh --yes` 真跑
3. 断言：`ls /etc/systemd/system | grep -c ttbox` = 0；`ls -d /run/ttbox-mouse-passthrough /lib/firmware/ttbox` 报不存在；`id ttbox` 失败
4. 用 1.4.7 包 + `ttbox_release_install.sh` 装回去，确认服务全 active

### S3 出货包含内部工具与文档（阻塞）

**根因（本轮新查清，比之前判断的更明确）：OTA 打包根本没有脚本。**

三套取文件的口径，互不统一：

| 环节 | 取文件规则 | 结果 |
|---|---|---|
| `scripts/ttbox_build_release.sh` | 只暂存 `bin/`（恰 1 文件）+ `lib/librknnrt.so` | 只管二进制 |
| `scripts/ttbox_fhs_init.sh` 的 `sync_tree` | **白名单闭集**：bin / lib / plugins / framework / ttbox_motion / usbproxy / scripts/edid + 指定脚本 + deploy/{keys,systemd,config} | 干净的安装树 |
| 1.4.7 的 OTA 包 | **手工 `tar` 整棵仓库树**（排除 tests / `__pycache__` / `*.pyc` / `.git`） | 368 文件，含全部内部物 |

板上 1.4.7 实测 368 个文件：

```
docs/ 123   plugins/ 81   scripts/ 42   usbproxy/ 28   platform/ 25
framework/ 19  deploy/ 17  modules/ 10  config/ 5   ttbox_motion/ 3
tools/ 8    bin/ 1   lib/ 1  + LICENSE / README.md / pyproject.toml / preview_server.py
```

对比定案：`tools/license/ttbox_license_gen.py`（发卡工具）、`tools/ota/ttbox_ota_sign.py`、`tools/ota/fake_ota_server.py`（定案 H-26 明写「不入包」）、`platform/`（定案 S1 起移出）、`docs/`（1.4 M 内部文档含探针脚本）**都不该在包里**。

因为打包是手工做的，所以「装机白名单」和「打包内容」之间没有任何机制保证一致——这就是根因。

**处置**：新增 `scripts/ttbox_pack_ota.sh` 作为**唯一打包入口**，并把白名单提成单一真源。

1. 把白名单抽成 `deploy/pack_manifest.txt`（一行一条，相对仓库根，支持目录）。
   `sync_tree` 与 `ttbox_pack_ota.sh` **都读这一份**，从此改一处两处都变。
2. `ttbox_pack_ota.sh` 的职责：
   - 按清单组装 `payload/`
   - 生成 `RELEASE_MANIFEST.json`（`files_sha256` 全量）放**包根**；发布树文件放 `payload/` 下；tar 成员**不带 `./` 前缀**（这三条是 1.4.7 联调踩出来的，见 `docs/交付前运行验证报告-2026-09-19.md:100-101`）
   - 调 `tools/ota/ttbox_ota_sign.py` 签名
3. **打包前置断言（fail-closed，任一条不过不出包）**：

| 断言 | 内容 |
|---|---|
| 禁内部物 | 包内不得出现 `docs/`、`tools/`、`platform/`、`modules/`、`tests/` |
| 禁密钥 | 包内不得出现 `*.priv.pem`、`.testkeys`、`id_rsa` |
| 禁垃圾 | 包内不得出现 `__pycache__`、`*.pyc`、`.git`、`*.bak-*`、`*.o`、`*.a`、`*.cmake` |
| `bin/` 闭集 | 恰 1 个文件，且是 `ttbox_core_main` |
| 数量自证 | 包内文件数 == 清单展开后的文件数（防漏防多） |

**白名单怎么定**（不能凭感觉删）：以 `sync_tree` 现有白名单为底，再补上板上实际被引用的路径。验证手段是板上 `grep -rn "/opt/ttbox/" /opt/ttbox/releases/1.4.7/` 找引用来源，凡是确实被运行时读取的目录必须进清单。`framework/`、`ttbox_motion/`、`usbproxy/` 已在 `sync_tree` 里，保留。

**验证**：`tar -tzf` 逐条对清单；板上装完后 `find /opt/ttbox/releases/1.4.9 -type f | wc -l` 与包内数一致；断言 `test ! -e /opt/ttbox/releases/1.4.9/{docs,tools,platform,modules}`。

### S5 本机 git 索引执行位全丢（阻塞）

### S7 版本号口径不统一（本轮新发现，出包前置）

**现象**：同一个系统上三处版本号不相同

| 位置 | 值 | 说明 |
|---|---|---|
| `core/CMakeLists.txt:14` `project(ttbox_core VERSION ...)` | **1.4.5** | 唯一的编译期真源，`version.hpp` 由它派生 |
| 板上 `/opt/ttbox/releases/` 目录名 | **1.4.7** | 打包/安装时手写的 |
| 面板 `/api/state` 的 `app_version` | **1.4.5** | `ttbox-web.py` 读 core 上报的版本 |

**影响**：用户打开面板看到「当前版本 1.4.5」，实际系统是 1.4.7，客服与售后无法对齐口径。
好消息是 OTA 的「是否已是最新」判定不看 core 版本，而是读 `/opt/ttbox/state/version`（`ttbox_ota_updater.py:94-126`，`new <= cur` 即跳过），所以不会造成重复下载；这纯粹是显示与文档口径问题。

**处置**：确立 `core/CMakeLists.txt:14` 为唯一真源，其余三处从它派生：

- 打包脚本（S3 里新增的 `ttbox_pack_ota.sh`）从 `core/CMakeLists.txt` 读版本号，写进 `RELEASE_MANIFEST.json`，并据此命名发布目录
- 面板的 `app_version` 继续读 core 上报值即可，不用改代码——只要 core 的版本号对了它就对了
- 出 1.4.8 时把 `core/CMakeLists.txt` 的版本号从 1.4.5 提到 1.4.8

**验证**：四处同值；面板 `/api/state` 的 `app_version` 与 `ls /opt/ttbox/releases/` 的目录名一致。

**处置结果（2026-09-19 晚收口）**：随 1.4.8 上板实测，板上 `readlink -f /opt/ttbox/current` = `/opt/ttbox/releases/1.4.8`、
面板 `/api/state` 的 `app_version` = `1.4.8`、包内 `RELEASE_MANIFEST.json` 的 `version` = `1.4.8`，三处一致。
出门前又提到 **1.4.9**（带心跳 403 分层修复，见 S8），同值性由 `ttbox_pack_ota.sh` 断言 5 与
`ttbox_conventions_gate.sh` 第 ⑥ 项（core 与 version.hpp 同值）自动钉住。

### S8 在线激活 1 分钟内掉授权（本轮新发现，P0，已修）

**现象**：板子用在线卡激活成功后，授权状态在 1 分钟内（有时一重启就）掉回 `restricted`；
服务端侧看到的会话行被置 `isValid=0`，盒子下一次心跳收 403「登录状态已失效」。

**根因（时区错配，不是 403 文案问题）**：同一张 `online_sessions` 表被两个进程用两套时区口径读写——

| 写入方 / 读取方 | 时区口径 | 结果 |
|---|---|---|
| 桥接层（`bridge`，mysql2） | `timezone:'Z'`，`NOW()` | 按 UTC 写 `lastHeartbeat` |
| license_system（Sequelize） | `timezone:'+08:00'` | 读回来把 UTC 值当本地时间 ⇒ 每条活跃会话**凭空老 8 小时** |

`license_system` 的 `scheduledTasks.js` 每分钟跑 `HeartbeatService.checkTimeout()`，
凡 `lastHeartbeat` 超过 `HEARTBEAT_TIMEOUT` 的行一律置 `isValid=0`。8 小时的误差远超任何阈值，
于是**每一条真实活跃的会话都会在下一轮清理里被判超时**。实测取会话 `id=23`：
Sequelize 读到的 `lastHeartbeat` 是 `2026-09-19T05:02:37Z`（差 8 小时），算出 age 29128s ≫ 180s ⇒ 判超时。

为什么之前没被发现：单测把 `health` 注入替换掉了，端到端只在板上跑过，而板端现象被归因成「403 文案歧义」。

**修复（三层，服务端为主）**：

| 层 | 改动 | 文件 |
|---|---|---|
| 根因 | Sequelize 时区 `'+08:00'` → `'+00:00'`，与桥接层 UTC 口径对齐 | 服务端 `license/api/src/config/database.js` |
| 阈值 | `HEARTBEAT_TIMEOUT` `30` → `180`（与桥接层下发的 180s 一致；30s 本身也过短） | 服务端 `license/api/.env` |
| 契约 | 桥接层把合成的 403 拆成两条：`强制下线` → 「会话已被强制下线」；`isValid!=1` → 「登录状态已失效」 | 服务端 `bridge/src/license.js` |
| 盒子自愈 | `HeartbeatWorker` 遇 403 先判是否「会话丢失」（`登录状态已失效`）⇒ 走 relogin 自愈（上限 3 次）；`强制下线/卡密到期` 仍直接锁 core | `plugins/web/lib/heartbeat_worker.py` |

最后一条是纵深防御：服务端修好之后正常不会再有会话被误置无效，但一旦发生，
盒子自己能靠卡密重新登录恢复，而不是把用户踢到未授权。

**验证**：服务端修完后板上实测 `online=True / core=active / valid=True` 连续 4 分钟跨多个清理周期不掉；
`heartbeat_worker` 新增 5 条单测在旧逻辑上全红、恢复后全绿（反向验证）。
随 **1.4.9** 上板做最终复测，证据见 `docs/交付前1.4.9真机复测报告-2026-09-19.md`（第六节）。

### S9 license 后端不是 systemd 托管（运维隐患，已修）

**现象**：`license_system` 后端（`node src/app.js`）是手工起在后台的孤儿进程（pid 9639），
`systemctl` 里查不到；服务器重启或进程崩溃后不会自拉起，面板与 `/api/` 一起挂掉。

**处置**：新增 `ttbox-license.service`（`Type=simple`、`WorkingDirectory=/opt/ttbox-server/license/api`、
`ExecStart=/usr/bin/node src/app.js`、`Restart=on-failure`），部署到
`/etc/systemd/system/` 并 `enable --now`。`.env` 由 dotenv 自动加载，无需 `EnvironmentFile`。
现役三个单元 `ttbox-bridge` / `ttbox-license` / `nginx` 均 `active`。

## 四、执行流程

### 4.1 按项目定死的八条规则

Windows 是源码唯一真源；本地能测的绝不上板；本地没 PASS 禁止交叉编译上板；RK3588 只跑交叉编译产物；板上只验真实硬件与真实环境；板端发现 Bug 必须回 Windows 改；每次修改都重新本地测试再重新交叉编译；没有真实证据不写 PASS。

### 4.2 本地门禁（每次改动后全跑，六条）

| 项 | 命令 | 通过标准 |
|---|---|---|
| 文档链接 | `python docs/check_links.py` | `broken_count=0` |
| 口径门禁九项 | `bash scripts/ttbox_conventions_gate.sh` | ①–⑨ 全 OK，退出码 0 |
| Core 单测 | `cd /c/ttbox-local/core && ctest --test-dir build-j --output-on-failure` | 29/29 passed |
| 平台层单测 | `python -m pytest --import-mode=importlib -q` | 92 passed |
| 面板单测 | `cd plugins/web && python -m pytest tests -q` | 267 passed |
| OTA 验签 | `python tools/ota/test_verify.py` | 10 组用例 0 失败 |

两个环境坑，写进 README 免得接手人误判：

- `ctest` 裸跑会报 29 个 `0xc0000135`（DLL 未找到），须先把 `/c/msys64/ucrt64/bin` 前置到 PATH
- `python -m pytest` 不加 `--import-mode=importlib` 收不到 `platform/tests`（stdlib 有同名 `platform` 模块）
- Core 本机构建在中文路径下要用 ASCII 符号链接 `C:/ttbox-local`，新增 target 必须重跑 `cmake -B build-j -G Ninja`

### 4.3 批次顺序

```
批 1  S2 + S5 + S3 + S7 代码改动
        ↓  本地六条门禁全绿
批 2  S4 换地址（等业主）       批 3  S1 清理 / 轮换 + 出厂自检（等业主决策）
```
